# バックエンドを Go とし、フロントとの型共有を TypeSpec 起点の OpenAPI で行う

- ステータス: 承認
- 日付: 2026-08-12 06:59
- 関連: [技術選定ガイド G-3](../docs/tech-decision-guide.md)、[モノレポ構成](./20260811-2015-monorepo-turborepo.md)

## コンテキスト

COPAN はフロントエンドとバックエンドを分離する。バックエンドの言語として、フロントと揃える TypeScript と、開発者が業務で使用している Go が候補となった。

言語を分けた場合、両者をまたぐ型の整合をどう保つかが問題になる。これを放置すると、APIのレスポンス形が変わってもフロントエンドが気づかず、実行時まで問題が発覚しない。

## 決定

1. **バックエンドの言語を Go とする。**
2. **APIの契約を TypeSpec で記述し、そこから OpenAPI 仕様を生成する。**
3. **OpenAPI から Go のサーバー側コードと TypeScript のクライアント側の型を生成し、生成処理を CI で検証する。**

```text
TypeSpec（唯一の情報源）
      │
      ▼
  OpenAPI 仕様
      ├──→ Go サーバーのインターフェース・型
      └──→ TypeScript の型・APIクライアント
```

## 理由

### Go を選ぶ理由

- **開発者が業務で使用しており、学習コストが低い。** 週5時間という制約下では、未知の要素を減らすことが最優先事項のひとつになる
- 個人開発で得た知見が業務に、業務で得た知見が個人開発に還流する。**学習を目的の一つに掲げる本プロジェクトの狙いに最も合致する**
- 画像のリサイズなど、ネイティブ実装に依存しがちな処理を制約なく書ける
- 起動が速いため、サーバーレス環境を選んだ場合もコールドスタートの影響が小さい

### 型共有に TypeSpec を選ぶ理由

言語が分かれる以上、型を直接共有することはできない。**スキーマを唯一の情報源とし、両側のコードを生成する**方式を取る。

OpenAPI を直接記述する方式と比較して、TypeSpec を挟む利点は以下。

- OpenAPI の YAML は冗長になりやすく、共通の型やエラーレスポンスの再利用が書きにくい。TypeSpec は型定義に近い記法で記述でき、**記述量と重複が減る**
- 生成されるOpenAPIの一貫性が保たれる

生成処理を CI で実行し、**コミットされた生成物と差分が出た場合に失敗させる**ことで、スキーマとコードの乖離を防ぐ。

## トレードオフとして受け入れること

- **TypeScript で統一する場合に比べ、初期構築の手間が増える。** 型を直接共有できず、生成のパイプラインを整備する必要がある
- **ビルド手順にコード生成という段階が増える。** 生成物をコミットするか否か、生成のタイミングをどうするかという運用ルールが別途必要になる
- **TypeSpec というレイヤーが1つ増える。** OpenAPI を直接書く場合より学習対象が増える。ただし、この設計自体を学習対象と位置づけているため許容する
- Go は Cloudflare Workers で公式にサポートされていない。**この決定により、APIの実行環境から Cloudflare Workers が除外される**（別ADRで扱う）

## 結果として必要になる決定

- APIの実行環境（Cloudflare Workers が使えないため、AWS 側で選定する）
- 生成物をリポジトリにコミットするか、CIで都度生成するか
- Go側のHTTPルーティング（生成コードが対応する形式に依存する）
