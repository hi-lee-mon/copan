# 実装は開発者本人が行い、Claude Code はチケット作成と支援に徹する

- ステータス: 承認
- 日付: 2026-08-12 09:05
- 関連: [Go採用](./20260812-0659-backend-go-openapi-contract.md)、[技術選定ガイド 判断軸5](../docs/tech-decision-guide.md)

## コンテキスト

COPAN は開発者1名、週5時間で進める個人開発であり、[技術選定ガイド](../docs/tech-decision-guide.md)の判断軸に「**学習の一般性**」を含めているとおり、**プロダクトの完成と同時に学習を目的としている**。

ここで AI エージェント（Claude Code）の使い方が問題になる。

- **実装を任せれば速い。** 週5時間という制約に対して、これは強い誘惑になる
- **しかし実装を任せると、学習という目的が達成されない。** 手が動くようになる過程が丸ごと失われる
- **一方、全てを自力でやると進まない。** 特に「何を調べればいいか分からない」時間が、週5時間を最も浪費する

この綱引きを曖昧にしたまま進めると、セッションごとに AI の関与度がブレ、結果としてどちらの目的も中途半端になる。**関与の境界を明文化する必要がある。**

## 決定

### 1. 実装は開発者本人が行う

**Claude Code はアプリケーションコードとテストコードを書かない。** 例外は、本人が明示的に「これは書いて」と指示した場合のみ。

Claude Code の役割は、チケットの作成、段階的なヒント、書かれたコードのレビュー、ADR・ドキュメントの起草、公式ドキュメントの確認に限定する。

### 2. 作業をチケット単位に分割し、チケットは Claude Code が作成する

チケットは `docs/tickets/NNN-<内容>.md` に markdown で置く。1枚あたり **2〜3時間**、1回の作業セッションで完結する粒度とする。

各チケットには以下を含める。

| 節 | 目的 |
| --- | --- |
| 目的 | 終わると何ができるようになるか |
| 背景 | どの要件・ADRから降りてきたか |
| 事前調査 | 仕組み・選択肢・公式ドキュメントの該当箇所 |
| 学習TODO | 着手前に理解しておくこと |
| 不足情報TODO | 進める前に埋めるべき決定・調査 |
| 実装ステップ | TDDの順序 |
| 完了条件 | 検証可能な形のチェックリスト |
| 振り返り | 完了時に本人が記入 |

### 3. 支援の仕方に4つのルールを課す

| # | ルール | 内容 |
| --- | --- | --- |
| 1 | **事前調査は骨組みまで** | 型・シグネチャ・構造体は提示してよい。**ロジックと設計判断は空欄にする** |
| 2 | **ヒントは段階的** | 方向性 → 該当箇所 → 擬似コード → 答え。求められるまで次の段階に進まない |
| 3 | **テストは本人が書く** | Claude はチケットに「テスト観点のリスト」を書くに留める |
| 4 | **完了条件は検証可能に** | コマンドと期待結果で書く。「〜できていること」で終わらせない |

## 理由

### なぜ「骨組みまで」なのか — 学習対象の非対称性

[Go採用のADR](./20260812-0659-backend-go-openapi-contract.md)に記録のとおり、**Go は開発者が業務で使用している言語であり、このプロジェクトの学習対象ではない。**

本当に未知なのは、バックエンド設計、AWS / Cloudflare、DB設計と PostGIS、認証、ログ設計、TypeSpec / OpenAPI、モノレポ構成である。

したがって、

- **関数シグネチャや構造体定義を Claude が示すことの学習損失は、ほぼゼロ。** これらは調べれば分かる定型であり、調べる時間は学習ではなく作業時間
- **テーブル設計・スコア設計・エラー設計を Claude が示すことの損失は致命的。** これらこそが学習対象そのもの

この非対称性に沿って線を引いた結果が「骨組みまで」である。

### なぜチケット化するのか

**本業の合間に進めるため、中断と再開が前提になる。** 中断のたびに「何をやっていたか」「次に何をするか」を再構築するコストが発生し、これが週5時間を削る。

1回の作業セッションで完結する単位に切っておけば、再開時に読むものが1ファイルに閉じる。進捗も枚数で測れる。

### なぜ事前調査をチケットに含めるのか

週5時間のうち、**最も無駄になるのは「何を調べればいいか分からない時間」**である。調査の入口（用語・公式ドキュメントの該当箇所・論点）を先に用意しておけば、限られた時間を理解と実装に使える。

これは答えを渡すことではない。**探索空間を絞ることと、答えを渡すことは違う。**

### なぜテストを本人が書くのか

テストを書くことは、**仕様を言語化すること**である。プロジェクトの規約でもテストコードには `What` を書くと定めており、これは設計を学ぶ核心部分にあたる。ここを渡すと、TDD を採用した意味の大半が失われる。

## 却下した案

| 案 | 却下理由 |
| --- | --- |
| **AI に実装させ、レビューで学ぶ** | 読んで分かることと、自分で書けることは別。特に設計判断は、迷って決めた経験としてしか残らない |
| **チケットを作らず、都度相談しながら進める** | 中断・再開のたびに文脈の再構築が必要。進捗が測れず、本業の合間という前提に合わない |
| **事前調査にコードを一切載せない** | 学習対象でない定型（Goのシグネチャ等）の調べ物に週5時間が溶ける。学習損失に見合わない |
| **事前調査に完成コードを載せる** | 写経に堕ちる。読んだ時点で分かった気になり、設計判断の経験が残らない |
| **GitHub Issues で管理する** | 現時点でリモートリポジトリが無く、先に作成が必要。ADRと置き場が分かれるのも避けたい。**リモートを作る段階で再検討する** |

## トレードオフとして受け入れること

- **開発速度は明確に落ちる。** AI に実装させれば数倍速い。これは学習と引き換えに意図的に払うコスト
- **チケットのレビューという工程が増える。** 作成は Claude が行うが、読んで妥当性を判断する時間は本人に発生する
- **事前調査が陳腐化しうる。** 先のチケットは前のチケットの決定に依存するため、**チケットは着手する直前に作る**運用で緩和する。まとめて先に作らない
- **進捗管理は markdown の手動更新になる。** ボードのような可視性は無い

## 結果として必要になる決定

- 1チケット2〜3時間という見積粒度の妥当性（数枚こなしてから見直す）
- GitHub Issues へ移行するか（リモートリポジトリを作成するタイミングで判断）
- チケットとブランチ・PRの対応づけ（CI構築時）
