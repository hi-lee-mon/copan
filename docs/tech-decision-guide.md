# COPAN 技術選定ガイド

最終更新: 2026-08-11

## 0. このドキュメントの目的

**技術を決めるためのドキュメントではなく、「何を決める必要があるのか」「それぞれをどういう観点で決めるのか」を整理するためのドキュメント。**

いきなり構成一式を決めるのではなく、

1. 要件から逆算して、必要な構成要素を洗い出す（本書 2章・3章）
2. 各要素について、判断すべき観点を明確にする（本書 3章）
3. 変えにくいものから順に、1つずつ決めていく（本書 4章）

という手順を取る。決定した内容は `docs/adr/` に記録する。

---

## 1. 全体に共通する判断軸

個々の選定は、原則としてこの6軸で評価する。

| # | 軸 | 内容 |
| --- | --- | --- |
| 1 | **要件適合** | そもそも要件を満たせるか。例: 地理空間検索ができないDBは候補から外れる |
| 2 | **開発時間** | 開発に割ける時間は**週5時間**。初期構築と学習にかかる時間が重い選択肢は、それ自体が不採用理由になる |
| 3 | **運用コスト** | 固定費が発生するか。無料枠の条件（**「非商用限定」でないか**）。実運用する方針のため規約は重要 |
| 4 | **可逆性** | 後から乗り換えられるか。**変えにくいものほど慎重に決める**（4章参照） |
| 5 | **学習の一般性** | その知識が他の現場でも通用するか。学習が目的の一つであるため、特定サービス固有の知識だけに寄せない |
| 6 | **既知からの距離** | フロントエンドの知識をどこまで流用できるか。未知の領域が多いほど、同時に導入する数を絞る |

軸が衝突したときは、**1 → 4 → 2 → 3 → 5 → 6** の優先順で判断する。
要件を満たさないものは論外であり、次に「後で直せないもの」を優先して守る、という考え方。

## 3. 構成要素の一覧と判断観点

可逆性は 高 = 後から容易に変更できる / 中 = 手間はかかるが可能 / 低 = 事実上やり直しに近い。

### A. 実行環境

> **どこでコードが動くのか。** フロントエンドしか経験がない場合、ここが最も馴染みの薄い領域になる。
> 「サーバーレス（リクエストごとに起動）」か「コンテナ（常時起動）」かで、この後のほぼ全てが変わる。

| ID | 決めること | 可逆性 | 判断観点 |
| --- | --- | :-: | --- |
| A-1 | フロントエンドのホスティング | 高 | SSR/SSGのどこまでが必要か / デプロイの速さ / プレビュー環境の有無 / 無料枠 |
| A-2 | APIの実行環境 | 中 | **サーバーレスかコンテナか** / コールドスタートの有無 / 実行時間の上限 / 使えるNode.js APIの範囲 / 固定費が発生するか / ローカルで同じ環境を再現できるか |

**特に理解しておくべき論点**: サーバーレス環境では「常駐プロセス」が持てない。つまり**DBのコネクションプールをアプリ内に持てない**（B-5に繋がる）。また、利用できるライブラリが制限される（Node.js固有APIに依存するライブラリが動かないことがある）。これがA-2の選択が他に波及する最大の理由。

### B. データ層

> **最も変えにくい領域。** データが入った後の移行は本当に大変なので、ここは時間をかけて決める。

| ID | 決めること | 可逆性 | 判断観点 |
| --- | --- | :-: | --- |
| B-1 | データベース製品 | **低** | **地理空間検索ができるか（最重要）** / 全文検索の能力 / 使わないときに課金が止まるか / サーバーレス環境から接続できるか / バックアップ |
| B-2 | 地理空間検索の実現方法 | 中 | 精度 / **インデックスが効くか**（効かないと全件走査になる） / クエリの書きやすさ / 「近い順にN件」が高速に取れるか |
| B-3 | ORM / クエリビルダ | 中 | 型安全性 / 実行環境で動くか / **生SQLの書きやすさ**（地理空間クエリはORMで書けないことが多い） / マイグレーション機能の有無 |
| B-4 | マイグレーション管理 | 中 | スキーマ変更履歴をどう残すか / 本番への適用手順 / ロールバック |
| B-5 | 接続方式（コネクションプーリング） | 高 | サーバーレスは**リクエストごとに接続を張ると接続数が枯渇する**。この対策をどうするか |

**B-2の選択肢の考え方**:
- 専用拡張（PostGIS等）を使う — 高機能・高速だが、DBがそれに対応している必要がある
- 緯度経度を持って自前で距離計算する — 単純だが、**インデックスが効かず全件走査になりがち**
- geohash等で近似的に絞り込む — 中間的。実装は自前

### C. 画像

> パンの写真が主役であり、**サービスのコストの大半を画像が占める**可能性が高い領域。

| ID | 決めること | 可逆性 | 判断観点 |
| --- | --- | :-: | --- |
| C-1 | 保存先（オブジェクトストレージ） | 中 | 保存料金 / **下り転送料金**（画像は重いのでここが効く） / CDNとの統合 |
| C-2 | 変換・最適化 | 高 | どこで処理するか（**アップロード時 or 配信時**） / リサイズ・フォーマット変換 / **EXIFのGPS除去は必須要件** |
| C-3 | 配信（CDN） | 高 | キャッシュ / 画像URLの設計 / 非公開画像を扱う必要があるか |
| C-4 | アップロード方式 | 中 | サーバー経由か、**署名付きURLでクライアントから直接送るか** / サーバーレスのリクエストサイズ上限 |

### D. 地図

| ID | 決めること | 可逆性 | 判断観点 |
| --- | --- | :-: | --- |
| D-1 | 地図ライブラリ | 高 | ラスタタイルかベクタタイルか / 表示するピンの数（多数のピンを扱えるか） / バンドルサイズ |
| D-2 | **地図タイルの配信元** | 中 | **規約（商用利用の可否）** / 料金と無料枠 / 自前配信が可能か / 日本のデータ品質 |

**D-2は要注意**。地図ライブラリ（Leaflet等）は無料でも、**表示するタイル画像の配信元は別問題**。
OpenStreetMap公式のタイルサーバーは、アプリケーションからの本番利用が想定されていない。

### E. 認証

| ID | 決めること | 可逆性 | 判断観点 |
| --- | --- | :-: | --- |
| E-1 | 認証方式 | 中 | メール+パスワード / OAuth（Google等） / マジックリンク。**投稿のハードルを下げる方針との整合** |
| E-2 | 実装手段 | **低** | ライブラリを使うか、外部SaaSか、自前か / 実行環境で動くか / **ユーザーデータがどこに保存されるか**（SaaSだと移行が難しい） / 課金体系（MAU課金か） |

**可逆性が低い理由**: ユーザーのアカウント情報が絡むため、後からの移行は再ログインを強いるなど実害が出る。また、メール送信（I-1）が必要になるかどうかがE-1で決まる。

### F. 非同期処理・バッチ

| ID | 決めること | 可逆性 | 判断観点 |
| --- | --- | :-: | --- |
| F-1 | 定期実行（cron） | 高 | OSMからの店舗データ取り込みに必要 / 実行時間の上限 |
| F-2 | キュー（重い処理の切り出し） | 高 | 画像処理や将来のAI処理をリクエスト内で完結できるか / リトライ / 失敗時の扱い |

**MVP時点では不要かどうかを見極める観点**: F-2は「リクエスト内で終わらない処理があるか」で決まる。無ければMVPでは作らない。

| ID | 決めること | 可逆性 | 判断観点 | 状態 |
| --- | --- | :-: | --- | --- |
| G-1 | モノレポツール | 高 | ビルドキャッシュ / タスク依存関係の管理 | **Turborepo で決定** |
| G-2 | パッケージマネージャ | 高 | モノレポのワークスペース対応 / インストール速度 / 実行環境との相性 | **pnpm で決定** |
| G-3 | **型共有の方式** | 中 | フロント/バック分離の最大の弱点をどう潰すか。**コード生成が必要か、不要か** / スキーマ定義の二重管理を避けられるか | |
| G-4 | テスト | 中 | ユニット / 統合 / E2E の役割分担 / **TDDで進める前提** / DBを使うテストをどう書くか | |
| G-5 | Lint / Format | 高 | 速度 / 設定の手間 | |

| G-7 | 環境分離とシークレット管理 | 中 | local / preview / production をどう分けるか / **本番の接続情報をどこに置くか** | |

## 4. 決定の順序

**可逆性が低いもの（後から変えられないもの）と、他を制約するものを先に決める。**

| 段階 | 決めるもの | 理由 |
| --- | --- | --- |
| **1** | A-2 APIの実行環境 | 他のほぼ全てを制約する。特にB（使えるDBと接続方式）とE（動く認証ライブラリ）が絞られる |
| **2** | B-1 DB製品 / B-2 地理空間検索の方法 | 可逆性が最も低い。かつコア機能の性能を決める |
| **3** | G-2, G-3, G-4, G-8 開発基盤の骨組み | **ここまで決まればスキャフォールドでき、TDDを開始できる** |
| **4** | E-1, E-2 認証 | 可逆性が低い。実装の最初の関門でもある |
| **5** | C 画像 / D 地図 | 機能実装と並行して決められる |
| **6** | F 非同期 / H 観測 / I その他 | v1.0に向けて順次 |

A-1（フロントのホスティング）は可逆性が高く、後回しでよい。

### 実装時に守る制約

DBの移行可能性を保つため、[20260812-0805](./adr/20260812-0805-database-neon-then-planetscale.md) により以下を**実装開始時から**守る。

- Neon 固有機能に依存しない（ブランチ機能は開発時の検証用途に限定）
- 本番のスキーマ管理はマイグレーションファイルで行う
- PostGIS は標準機能のみ使う
- 接続情報は環境変数で抽象化する
