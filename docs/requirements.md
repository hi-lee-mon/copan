# コパン（COPAN）要件定義書 v1

最終更新: 2026-08-11

> **名前の由来**: フランス語 *copain*（仲間）の語源は後期ラテン語 *compāniō* = **com-（共に）+ pānis（パン）**、すなわち「パンを分け合う相手」。
> 英語 *companion*、イタリア語 *compagno* も同語源。プロダクトのコンセプトそのものを名前が表している。
> 命名の経緯と却下案は [ADR 20260811-2003](./adr/20260811-2003-product-name.md) を参照。

---

## 0. 一文定義

> **コパンは、パン好きが現在地や投稿を通じて、まだ知らないパンと出会い、記録・共有するためのパン特化型サービスです。**

### プロダクト判断基準

新しい機能・仕様を検討するときは、常にこの問いに答える。

> **「この機能は、パンとの新しい出会いを増やすか？」**

Noなら作らない。判断に迷ったら本ドキュメントの「4. やらないこと」を先に読む。

---

## 1. 背景

パン屋を探す手段は既に複数あるが、いずれも「パン好き」の目的とはズレている。

| 手段 | 得意なこと | パン好きにとっての課題 |
| --- | --- | --- |
| Google Maps | 近くの店を探す | 「パン」ではなく「店」が中心 |
| グルメサイト | 店・口コミを調べる | パン単位で探しにくい |
| Instagram | おいしそうなパンとの出会い | 現在地との関係が弱い |
| 個人ブログ等 | 詳細な情報 | 情報が分散している |

街を歩いていて「この辺に美味しそうなクロワッサンないかな？」と思ったとき、簡単には探せない。
一方SNSには大量のパン写真がある。

**「パンの写真による発見」と「現在地からの探索」を組み合わせる** のがコパンの出発点。

---

## 2. 目的

> **パン好きが、まだ知らないパンと出会える機会を増やすこと。**

コパンが作るのは以下の循環であり、SNSは目的ではなく**出会いを増やすための仕組み**として位置づける。

```text
現在地から探す
    ↓
おいしそうなパンに出会う
    ↓
パン屋へ行く
    ↓
パンを食べる
    ↓
記録・共有する
    ↓
その投稿から別の人がパンを発見する
```

### 3つの狙い

1. **「店」ではなく「パン」から探せるようにする**
   「近くのパン屋」ではなく「近くにある、おいしそうなクロワッサン」を探せる。これが既存の地図サービスとの最大の違い。
2. **検索しなくてもパンと出会えるようにする**
   ユーザーが能動的に検索しなくても、現在地周辺のパンがタイムラインに流れてくる。**検索から発見へ**。
3. **ユーザー投稿によってパン情報を蓄積する**
   店舗側の情報入力を前提にしない。UGCとして使われるほどコパン独自のパンデータが充実する。

---

## 3. ターゲット

一般的なグルメユーザーは狙わず、**パンが好きな人に限定**する。

| 項目 | 想定 |
| --- | --- |
| パンへの関心 | 高い |
| 行動 | パン屋巡りをする |
| 新規開拓 | 好き |
| SNS | Instagram等でパンを見る・投稿する |
| 外出 | 外出先でもパン屋を探す |
| 年齢 | 年齢で強く限定しない |

典型像は「休日に出かけたら、近くに良さそうなパン屋がないかつい調べてしまう人」。

### 初期に特に重要な層

**パンを食べる人より、パンを記録する人**を優先する。

- パン屋巡りが趣味
- 食べたパンを写真に撮る
- Instagram等にパンを投稿している
- 新しいパン屋を開拓するのが好き
- おすすめのパンを人に教えるのが好き

この層の投稿がコパンのコンテンツを形成する。

---

## 4. やらないこと

**食べログのパン版を目指さない。** 初期段階では以下を明確に対象外とする。

- 長文レビューを中心にしない
- 星5段階の店舗評価を中心にしない
- 飲食店全般に広げない
- パン以外の料理を扱わない
- 店舗検索をプロダクトの中心にしない
- 店舗側の情報入力を前提にしない

---

## 5. リリース計画

コールドスタート問題（投稿ゼロのエリアではコア体験が成立しない）への対策と開発を兼ねるため、**2段階でリリースする**。

| | 位置づけ | ゴール | 目安 |
| --- | --- | --- | --- |
| **v0.1** | 非公開・自分専用 | 自分がパンを記録する道具として完成させ、対象エリアのシードデータを作る | 約2ヶ月 |
| **v1.0** | 一般公開 | 発見体験（タイムライン・地図・保存）を載せて公開する | さらに約2ヶ月 |
| v1.1〜 | 継続強化 | AI自動タグ付け、ソーシャル機能、ゲーミフィケーション | 以降 |

v0.1を「シードデータ作成ツール」と位置づけることで、**開発とコンテンツ準備が同じ作業になる**。

### 対象エリア

初期は**全国対応しない**。開発者自身の生活圏に限定し、狭い範囲で投稿密度を作ることを優先する。
（具体的な範囲は「11. 未決事項」参照）

## 6. 機能要件

◎ = 必須、○ = 余力があれば、× = 対象外

### v0.1（自分専用・非公開）

| 分類 | 機能 | | 概要 |
| --- | --- | :-: | --- |
| アカウント | ユーザー登録・ログイン | ◎ | アカウント作成と認証 |
| 投稿 | 写真投稿 | ◎ | 食べたパンを写真で投稿 |
| 投稿 | 画像最適化・EXIF除去 | ◎ | 配信用リサイズ。**GPS情報は必ず除去する** |
| 投稿 | 近隣店舗候補 | ◎ | 現在地から近いパン屋を候補表示 |
| 投稿 | パン屋紐付け | ◎ | 投稿と店舗を関連付ける |
| 投稿 | **新規店舗追加** | ◎ | 候補に無い個人店を投稿時に追加できる。これが無いと投稿が詰まる |
| 投稿 | パン種類設定 | ◎ | クロワッサン、カレーパン等のカテゴリ／タグ |
| 記録 | 自分の投稿一覧 | ◎ | 自分の記録を時系列で確認 |
| データ | 店舗マスタ取り込み | ◎ | OpenStreetMapからパン屋データを取り込むバッチ |

### v1.0（一般公開）

| 分類 | 機能 | | 概要 |
| --- | --- | :-: | --- |
| 発見 | パンタイムライン | ◎ | パン写真を主役に表示。並び順は**距離と鮮度の両方**を考慮 |
| 発見 | 現在地周辺表示 | ◎ | 近くで投稿されたパンを表示 |
| 発見 | 距離表示 | ◎ | パン屋までの距離を表示 |
| 発見 | パンタグ表示・絞り込み | ◎ | パン種類による絞り込み |
| 発見 | **0件フォールバック** | ◎ | 近くに0件なら半径を段階的に広げる。空の画面を出さない |
| 地図 | パンマップ | ◎ | 周辺のパン・パン屋を地図表示（Leaflet + OpenStreetMap） |
| 地図 | **未投稿店舗の表示** | ◎ | まだ誰も投稿していないパン屋を「未開拓」として表示する |
| SNS | **保存** | ◎ | 後で食べたいパンを保存。ユーザー数が少ない時期でも単独で価値がある |

| 運営 | 通報・削除導線 | ◎ | UGCを公開する以上、公開時点で最低限必要 |
| SNS | いいね | ○ | 気になるパンにリアクション |
| 検索 | パン種類検索 | ○ | 「クロワッサン」等から探す |
| 探索 | スワイプ | ○ | 写真をスワイプしてパンを発見 |

### v1.1以降（対象外）

| 分類 | 機能 | 備考 |
| --- | --- | --- |
| AI | 写真からパン種類・タグを自動推定 | **優先度が高い。**「投稿を極限まで簡単にする」に直結する |
| AI | 好みに基づくパンの推薦 | 投稿データが溜まってから |
| SNS | コメント / フォロー | |
| 探索 | パンガチャ / パンレーダー | |
| ゲーム | パン図鑑 / パン巡り | 「未開拓の店」という概念と接続できる |
| リアルタイム | 焼き上がり情報・通知 | データ確保後。将来的に店舗連携も検討 |
| 店舗 | 店舗公式アカウント / PR投稿 / 取り置き | マネタイズ段階 |

## 7. ユーザーストーリー

### US-1 発見

> パン好きとして、現在地の近くにあるパンを写真から眺めたい。知らなかった美味しそうなパンと出会いたいから。

**受け入れ条件**
- アプリを開くと、現在地周辺で投稿されたパンが写真主体で一覧表示される
- 各パンに店舗までの距離が表示される
- 周辺に投稿が無い場合でも、半径を広げた結果か未開拓のパン屋が表示され、空の画面にならない

### US-2 探索

> パン好きとして、美味しそうなパンを見つけたとき、そのパンを売っている店の場所を知りたい。実際に買いに行きたいから。

**受け入れ条件**
- パンの詳細から店舗情報と地図上の位置に到達できる
- 経路案内（外部地図アプリ連携）に遷移できる

### US-3 投稿

> パン好きとして、食べたパンを写真とパン屋情報と一緒に簡単に投稿したい。自分の記録を残し、他のパン好きにも共有したいから。

**受け入れ条件**
- 「写真を選ぶ → 近くのパン屋から選ぶ → パン種類を選ぶ → 投稿」で完了する
- 長文入力を必須にしない
- 候補に店が無い場合、その場で新規店舗を追加して投稿を続行できる

### US-4 保存

> パン好きとして、気になったパンを保存しておきたい。後日そのパンを食べに行きたいから。

**受け入れ条件**
- 一覧・詳細のどちらからでも保存できる
- 保存した一覧を、現在地からの距離順で見られる

## 8. UI/UXの基本思想

### パンが主役

店名より先に**パン写真を見せる**。

```text
┌──────────────────────┐
│                      │
│    🥐 パンの写真       │
│                      │
├──────────────────────┤
│ クロワッサン           │
│ ○○ベーカリー · 320m   │
│ ☆ 保存      ♡ 128     │
└──────────────────────┘
```

「○○ベーカリーがあります」ではなく **「こんなパンが320m先にあります」** という体験にする。

### 投稿は極限まで簡単にする

```text
写真を選ぶ → 近くのパン屋から選ぶ → パン種類を選ぶ → 投稿
```

長文レビューは要求しない。将来的にAIによる自動タグ付けで、さらに手数を減らす。

## 9. 主要な設計方針（決定事項）

### 9.1 コールドスタート対策

3つを併用する。

1. **エリア限定** — 対象エリアを開発者の生活圏に絞り、狭い範囲で密度を作る
2. **自己シード** — v0.1を使って開発者自身が投稿を蓄積してから公開する
3. **未投稿店舗の表示** — OSM由来のパン屋を「まだ誰も投稿していないパン屋」として地図に出す

3により、投稿ゼロの状態が「空っぽの画面」ではなく **「未開拓エリア」という意味のある画面** になる。これは将来のパン図鑑・パン巡りへの布石にもなる。

### 9.2 店舗マスタ

**OpenStreetMap を土台とし、不足分をユーザーが追加する**ハイブリッド構成。

- OSMから対象エリアのパン屋（`shop=bakery` 等）を抽出し、自前DBに取り込む
- 候補に無い店はユーザーが追加できる（v0.1から必須）
- ユーザー追加店舗とOSM由来店舗はデータソースを区別して保持する
- 重複店舗のマージ手段を運営側に用意する（初期は手動で可）

データを自前資産として蓄積でき、外部APIの規約・従量課金リスクを負わない構成とする。

### 9.3 投稿の鮮度

パンは日替わりで売り切れる。**1年前の投稿を根拠に「320m先にクロワッサンがあります」と見せるのは、体験としては誤りに近い。**

- タイムラインの並び順は **距離と鮮度の両方** をスコアに含める
- 新しい投稿にはバッジを付ける等、鮮度を視覚的に区別する
- 古い投稿は「今そこにある」ではなく「過去にあった」として見せる

コパンの投稿は**ストック型（店舗評価）ではなくフロー型（鮮度が価値）**である、と位置づける。

### 9.4 0件を出さない

現在地周辺の検索結果が0件の場合、半径を段階的に拡大する。それでも0件なら未投稿のパン屋を表示する。
**「何も無い画面」をユーザーに見せない**ことを設計上の制約として扱う。

## 10. 非機能要件

### 性能
- 周辺パン検索のレスポンス: p95 で 500ms 以内を目標
- 画像は用途別サイズを事前生成し、CDN経由で配信する
- 地理空間検索はインデックスを用いる（全件スキャンをしない）

### 可用性
- 個人開発のためSLAは定めない
- ただしエラー率とレイテンシの監視、および通知は入れる

### セキュリティ
- 認証必須の操作と匿名で閲覧可能な範囲を明確に分ける
- 投稿・画像アップロードにレート制限を設ける
- アップロード画像のMIME・サイズ・実体を検証する

### プライバシー
- **ユーザーの現在地はサーバーに保存しない**（検索条件として都度受け取るのみ）
- **アップロード画像からEXIFのGPS情報を必ず除去する**
- 公開される位置情報は「店舗の位置」であり、「投稿者の位置」ではない

### 運用・コンテンツ
- 公開時点で通報導線と運営による削除手段を用意する
- 利用規約・プライバシーポリシーを公開時までに整備する

### ログ・計測
- 構造化ログ（JSON）とリクエストIDによる追跡
- プロダクト指標として最低限これを計測する:
  - 投稿数 / 投稿ユーザー数
  - タイムライン表示 → パン詳細 → 店舗情報への遷移率（＝「出会い」の成立率）
  - 保存数、保存からの再訪率
  - 周辺検索の0件率とフォールバック発動率

### コスト
- 月額上限を設定し、超過が見込まれる場合はアラートを出す
