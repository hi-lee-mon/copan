# Lambda を含む AWS のリソースを Terraform で管理する

- ステータス: 承認
- 日付: 2026-08-16 00:17
- 関連: [20260812-0712 インフラ構成](./20260812-0712-infrastructure-cloudflare-aws-hybrid.md)、[20260812-0805 データベース](./20260812-0805-database-neon-then-planetscale.md)、[20260812-1324 バージョン固定と audit](./20260812-1324-version-pinning-and-audit.md)、[20260812-0905 開発の進め方](./20260812-0905-development-workflow.md)、[20260815-1906 Lambda アダプタとランタイム](./20260815-1906-lambda-adapter-and-runtime.md)、[技術選定ガイド G-6 / G-7](../tech-decision-guide.md)、[チケット 007](../tickets/README.md)（未作成）

## コンテキスト

[20260812-0712](./20260812-0712-infrastructure-cloudflare-aws-hybrid.md) で計算層は **AWS Lambda（VPC外）+ Function URL** に決まっているが、**AWS 上のリソースはまだ1つも作っていない。** 003 で Lambda 用のバイナリがビルドできる状態までは来ており、次に「そのバイナリを載せる先をどう作るか」を決める必要が出た。

制約は次のとおり。

- **配信層は Cloudflare、計算層は AWS のハイブリッド構成**（[20260812-0712](./20260812-0712-infrastructure-cloudflare-aws-hybrid.md)）。AWS 専用のツールを選ぶと、Cloudflare 側が管理の外に残る
- **開発は週5時間・1名。** [技術選定ガイド](../tech-decision-guide.md)は「過剰な設計を持ち込まない」ことを求める一方、判断軸5に**学習の一般性**を置いている
- **バージョンの真実は `mise.toml` に集約する**（[20260812-1324](./20260812-1324-version-pinning-and-audit.md)）
- **v0.1 は非公開・自分専用。** 環境は本番1つで足りる可能性が高い
- **v1.0 の前に DB を東京リージョンへ移す予定がある**（[20260812-0805](./20260812-0805-database-neon-then-planetscale.md)）。周辺のリソースを作り直す場面が実際に来る

## 決定

### 1. AWS のリソースは Terraform で管理する

対象は 007 以降で作るもの全部。Lambda 関数、Function URL、実行ロール（IAM）、CloudWatch Logs のロググループなどを含む。

### 2. マネジメントコンソールでの手作業を、正の状態としない

調査や動作確認でコンソールを触るのは構わない。ただし**恒久的に残る設定をコンソールで作らない**。作ってしまった場合は Terraform 側に取り込むか、消して作り直す。

### 3. Terraform 本体のバージョンは `mise.toml` で固定する

[20260812-1324](./20260812-1324-version-pinning-and-audit.md) の「バージョンの真実は `mise.toml`」をそのまま適用する。mise は `terraform` を登録済みのツールとして扱えるため、Node・pnpm・Go と同じ扱いにできる。**具体的な値は 007 の着手時点の最新を採る**（本 ADR を書いた時点では 1.15.8）。

### 4. Cloudflare 側を Terraform に含めるかは、本 ADR では決めない

R2 バケットやフロントの公開設定を実際に作る段（v0.1 の画像投稿・フロント公開）で判断する。

## 理由

### なぜコンソールの手作業ではなく IaC なのか

- **半年後に「この Lambda のメモリはいくつだったか」を調べる先がコードになる。** ADR を書いている理由と同じ
- **作り直せること自体が可逆性である。** [20260812-0712](./20260812-0712-infrastructure-cloudflare-aws-hybrid.md) は Lambda を選んだが、そこから離れられる状態を保ちたい。手作業で作ったものは、消したら二度と同じものを再現できない
- **作り直す場面が予定されている。** [20260812-0805](./20260812-0805-database-neon-then-planetscale.md) の DB 移行がそれにあたる

### なぜ Terraform なのか

**決定打は、AWS と Cloudflare を1つのツールで管理できることにある。** [20260812-0712](./20260812-0712-infrastructure-cloudflare-aws-hybrid.md) のハイブリッド構成では、AWS 専用ツール（SAM / CDK）を選んだ時点で配信層が管理の外に残り、**インフラの記述が2つの流儀に割れる**。Terraform には公式の Cloudflare provider があり、この構成で唯一「1つの書き方で両方を書ける」選択肢になる。

判断軸に照らすと次のとおり。

| 軸 | 評価 |
| --- | --- |
| 要件適合 | ハイブリッド構成を1つのツールで書ける（上記） |
| 可逆性 | HCL と state は OpenTofu と互換。乗り換え先が実在する |
| 開発時間 | SAM より手数は多い（トレードオフ参照） |
| 運用コスト | CLI 自体は無料。state を S3 に置いても月数円 |
| 学習の一般性 | **業務で最も遭遇する IaC。** 判断軸5に最も強く合致する |
| 既知からの距離 | 未知だが、AWS の学習範囲は Lambda・IAM・SDK に限ると [20260812-0712](./20260812-0712-infrastructure-cloudflare-aws-hybrid.md) が既に定めており、範囲は限定されている |

## 却下した案

| 案 | 利点 | 却下の理由 |
| --- | --- | --- |
| **AWS SAM** | Lambda に最適化されており、`sam deploy` の手数が最も少ない。ローカル実行の支援もある | **AWS 専用で Cloudflare を管理できない。** また CloudFormation の上に乗るため、詰まったときに CFn のエラーを読むことになり、**学習対象が2層になる** |
| **AWS CDK** | TypeScript で書けるためモノレポと相性がよく、`packages/` に置ける | 同じく AWS 専用。加えて抽象度が高く、生成される CloudFormation が読みにくい。**週5時間に対して、抽象の裏側まで学ぶ余力がない** |
| **Serverless Framework** | Lambda のデプロイ設定が最も短く書ける | v4 で商用ライセンスに変わった（一定売上未満は無料だが登録が必要）。AWS 専用である点も SAM と同じ |
| **Pulumi** | 汎用言語で書けるため、型と IDE の支援が効く | 情報量・事例・求人が Terraform に劣る（判断軸5）。**この構成で Terraform より良くなる点を示せない** |
| **OpenTofu** | MPL-2.0 で Linux Foundation 管理。BSL を避けられる。state 暗号化など Terraform に無い機能もある | 判断軸5（学習の一般性）で Terraform が優位。**個人開発では BSL の競合利用制限が実質的に効かない**ため、避ける動機が弱い。なお **HCL と state に互換性があり後から乗り換えられる**ので、今決め込む必要がない |
| **コンソールで手作業** | 最初の1回は最速 | 再現性がない。003 で「デプロイより先にローカル実行を確立する」と決めたのと同じ理由で、**後で必ず高くつく** |
| **AWS CLI のシェルスクリプト** | 追加のツールが要らない | **差分を検知できず、「今どうなっているか」を保持しない。** 作り直しはできても、変更ができない |

## トレードオフとして受け入れること

- **Lambda のデプロイは SAM より手数が多い。** zip の作成と、その内容が変わったことを Terraform に伝える仕組み（`source_code_hash` 相当）を自分で書く必要がある
- **学習対象が増える。** HCL・state・provider・IAM ポリシー。週5時間に対する負荷は小さくない。ただし [20260812-0905](./20260812-0905-development-workflow.md) が学習を目的に据えており、AWS の学習範囲は [20260812-0712](./20260812-0712-infrastructure-cloudflare-aws-hybrid.md) が Lambda・IAM・SDK に限定している
- **state という、壊れると困る資産を持つことになる。** 失うと既存リソースを掌握できなくなる。**置き場所の決定（未決）が、そのまま事故率になる**
- **鶏卵問題が生じる。** state を S3 に置くなら、その S3 バケット自体は Terraform の外で作るか、ローカル state で作ってから移すことになる
- **ライセンス上の不確実性を引き受ける。** Terraform は 2023年8月に BSL へ移行し、2024年12月に IBM が HashiCorp の買収を完了している。**逃げ道は OpenTofu への移行**で、HCL と state の互換性がそれを担保する

## 結果として必要になる決定

いずれも **007（デプロイ）のチケットを作る時点**で決める。

- **state をどこに置くか。** S3 + `use_lockfile`（Terraform 1.11 で GA。DynamoDB のロックテーブルは不要になった）/ HCP Terraform / ローカル。**1名開発なのでロックが要るかどうかから検討する**
- **ディレクトリをどこに置くか**（`infra/` を新設するか、`apps/api/` の中か）。turbo のワークスペースに含めるかも併せて
- **環境を分けるか。** v0.1 は本番1つで足りるか（G-7 と重なる）
- **`terraform apply` を誰が実行するか。** 手元だけか、CI からか（G-6 と重なる）
- **AWS の認証情報の扱い。** 手元のプロファイル、CI から流すなら OIDC
- **Lambda のコードをどう渡すか。** zip を Terraform 側で作るか、事前に作った zip を参照するか、S3 を経由するか
- **Cloudflare を Terraform に含めるか**（v0.1 の画像投稿・フロント公開の段で判断）
