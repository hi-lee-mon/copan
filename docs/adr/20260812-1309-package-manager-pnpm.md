# パッケージマネージャに pnpm を採用する

- ステータス: 承認
- 日付: 2026-08-12 13:09

## コンテキスト

[20260811-2015](./20260811-2015-monorepo-turborepo.md) で Turborepo を採用したが、**その下で依存を解決するパッケージマネージャ（技術選定ガイドの G-2）は未決**だった。

前提として、Turborepo とパッケージマネージャは責務が違う。

|                                  | 担当                                             |
| -------------------------------- | ------------------------------------------------ |
| パッケージマネージャのワークスペース | 依存の解決とインストール。パッケージ間の参照     |
| Turborepo                        | タスクの依存グラフとキャッシュ。**依存解決はしない** |

Turborepo はパッケージマネージャの代替ではなく、その上に乗るタスクランナーであるため、G-2 は別途決める必要がある。

現在の環境には pnpm 10.13.1 と npm 11.5.2（Node.js 24.4.0 同梱）の両方がある。

このリポジトリは今後、`apps/web`（Next.js）、`apps/api`（Go）、`packages/*`（TypeSpec の定義と生成された TS の型）という構成になる予定で、**パッケージ間の参照関係が増えていく**。特に生成物のパッケージは、参照する側が依存として宣言し忘れやすい。

## 決定

**pnpm を採用する。** ワークスペースは `pnpm-workspace.yaml` で定義する。

## 理由

- **ファントム依存を構造的に防げる。** npm はフラットな巻き上げにより、`package.json` に書いていない依存を `node_modules` 直下から import できてしまう。pnpm はグローバルストアへのシンボリックリンクで `node_modules` を構成し、リンクされるのは `package.json` に宣言されたものだけになる
  - モノレポで効く。TypeSpec の生成物パッケージを `apps/web` が「宣言せずに使えてしまう」状態は、npm では検出できない。CI で新規クローンしたときや依存の巻き上げ位置が変わったときに壊れる
- **Turborepo 公式ドキュメントが pnpm を前提にした記述を主にしている。** [20260812-1305](./20260812-1305-go-in-turborepo-workspace.md) で「公式パターンから逸脱しない」と決めており、同じ理由が適用される
- **インストール速度とディスク使用量で有利。** コンテンツアドレス可能なストアにより、パッケージの実体はマシン内で1つになる
- **可逆性が高い。** 移行するなら lockfile を作り直し、ワークスペース定義を `package.json` の `workspaces` に移すだけで済む。G-2 は技術選定ガイドで可逆性「高」に分類されている

## 却下した案

### npm workspaces

Node.js 24 に同梱されており追加インストールが不要。判断軸「既知からの距離」では最も近い。

**却下の理由**: ファントム依存を防げないこと。上に書いたとおり、このリポジトリは生成物パッケージを持つ構成になるため、この弱点が具体的な事故の形を持っている。追加インストールの手間は pnpm が既に環境にある時点で発生しない。インストール速度とディスク効率でも劣る。

### yarn / bun

環境に無く、導入コストが pnpm と同等以上でありながら、上記の利点を上回るものがない。bun は実行環境としての魅力があるが、本プロジェクトのフロントは Cloudflare、API は Go であり、bun のランタイムを活かす場面がない。

## トレードオフとして受け入れること

- **npm からの学習コストがかかる。** シンボリックリンク構造に起因する問題（一部ツールが実体パスを前提にする）に遭遇したとき、原因の切り分けに時間を要する
- **pnpm 10 から、依存パッケージの lifecycle スクリプトが既定で実行されない。** Rspack のサプライチェーン攻撃への対応として入った破壊的変更。`postinstall` でバイナリを取得する類のパッケージ（esbuild、prisma、sqlite3 など）は、`package.json` の `pnpm.onlyBuiltDependencies` に明示的に列挙しないと動作しない

  ```jsonc
  {
    "pnpm": {
      "onlyBuiltDependencies": ["esbuild"],
    },
  }
  ```

  **「インストールは成功したのに動かない」という形で出る**ため、原因に気づきにくい。ただしこれは既定で安全側に倒す変更であり、受け入れる
- **CI で pnpm のセットアップが1ステップ増える**（`pnpm/action-setup`、または Corepack）
