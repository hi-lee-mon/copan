「生成物はコミットし、**CI で再生成して差分が出たら失敗させる**」（[CLAUDE.md の制約](../../CLAUDE.md)）を実現する仕組みが、これまで一度も存在しなかった。複数の ADR が同じ穴をチケット 006 に預けている。

加えて、**リモートリポジトリがそもそも存在しなかった**（実測: `git remote -v` が空）。CI はリモートで走るものなので、その作成もここに含まれる。

決めるべきことは連鎖している。**公開範囲 → CI をどこで動かすか → トリガとブランチ運用 → ジョブ構成 → 差分チェックの書き方**の順に上流が下流の形を決めるため、1本の ADR にまとめる。

制約は次のとおり。

- 開発は**週5時間・1名**。[技術選定ガイド](../tech-decision-guide.md)は「過剰な設計を持ち込まない」ことを求めている
- 名称は「**仮の COPAN**」の段階で、商標の実査は v1.0 公開準備前まで繰り延べ済み（[20260814-1826](./20260814-1826-defer-trademark-research.md)）
- ツールのバージョンは `mise.toml` に集約し、**CI も同じファイルを読む**（[20260812-1324](./20260812-1324-version-pinning-and-audit.md)、[20260815-1420](./20260815-1420-go-version-and-module-path.md)）

## 決定

### 1. リモートリポジトリは GitHub の **private**

### 2. CI は **GitHub Actions**。ワークフローは `.github/workflows/ci.yml` の1枚

技術選定ガイド **G-6「CI/CD」のうち「どこで動かすか」がこれで決まる**。デプロイ（CD）は本 ADR の範囲外で、チケット 007 が扱う。

### 3. トリガは **`main` 向けの `pull_request` と、`main` への `push`**。作業はチケット単位のブランチで行う

ブランチ名はチケット番号を含める（例: `006-ci`）。[20260812-0905](./20260812-0905-development-workflow.md) が残した「チケットとブランチ・PR の対応づけ」は**これで決着**する。

### 4. ジョブは **1つ**。checkout → mise → `pnpm install` → 作り直し → 差分判定 → テスト → `pnpm audit` を直列に並べる

ステップは「**1ステップ＝1つの検証**」の粒度に分け、`name:` を付ける。

### 5. 検証するのは3つ

| 検証 | コマンド |
| --- | --- |
| 生成物が最新か | `pnpm exec turbo run build --force` → `git status --porcelain` が空であること |
| テストが通るか | `pnpm exec turbo run test` |
| Node の依存に脆弱性が無いか | `pnpm audit --audit-level=high` |

### 6. 作り直しは **`--force` を付ける**。`turbo.jsonc` の `outputs` は `dist/**` のまま変えない

### 7. action は**タグで固定する**（`actions/checkout@v7.0.1` / `jdx/mise-action@v4.2.5`）。`actions/setup-node` / `setup-go` / `pnpm/action-setup` は使わない

### 8. turbo の**リモートキャッシュは使わない**

### 9. Go の脆弱性チェック（`govulncheck`）は **006 に入れない**。別チケットに切り、**v0.1 の投稿機能に入る前**に扱う

### 10. チケット管理は **`docs/tickets/` の markdown のまま**。GitHub Issues には移行しない

## 理由

### 1. private — [20260814-1826](./20260814-1826-defer-trademark-research.md) と判断を揃える

同 ADR は「不可逆なので**ドメイン・SNS アカウントは取得しない**」と決めている。public リポジトリは、リポジトリ名という形で「コパン／COPAN」を世に出す行為であり、**商標の実査前に名称を露出させる**点で同じ性質を持つ。実査の結果が黒なら、公開済みの名称は取り消せない。

課金は判断材料にならなかった。GitHub Free プランは private でも**月 2,000 分**の Actions が無料で、1回2〜3分の実行なら上限に遠い（public は標準ランナーが無制限に無料）。

### 2. GitHub Actions — 設定がリポジトリに同居し、既存 ADR が既にこれを前提にしている

- **ワークフローが `.github/workflows/*.yml` としてリポジトリに入る。** CI の変更が普通の差分としてレビューでき、ADR・チケットと同じ場所で履歴に残る
- [20260812-1324](./20260812-1324-version-pinning-and-audit.md) が「CI も `jdx/mise-action` で同じ `mise.toml` を読む」と決めており、[20260815-1420](./20260815-1420-go-version-and-module-path.md) も「CI の Go セットアップを `jdx/mise-action` に寄せる」と書いている。**GitHub Actions を前提にした決定が既に2本ある**
- リポジトリと CI の提供元が同じなので、セットアップが1つ減る（外部 CI ならリポジトリとの連携設定が要る）

### 3. PR を挟む — 目的はレビューではなく「**赤い CI をマージ前に見る**」こと

開発者は1名なのでレビュアーはいない。それでも PR を挟むのは、**`main` が常に緑である状態を保つため**である。`main` に直接 push すると、CI が赤いと分かるのは既に `main` に入った後になる。スキャフォールドのゴールは「本番URLの `/healthz` が 200 を返す」であり、**`main` からデプロイする以上、`main` が壊れている時間は短いほどよい**。

チケット単位でブランチを切ることで、[20260812-0905](./20260812-0905-development-workflow.md) の運用（1チケット2〜3時間）とブランチの寿命が一致する。

### 4. 1ジョブ — セットアップの重複が実行時間を支配する

実測（2026-08-30、手元）:

| 対象 | 時間 |
| --- | --- |
| `turbo run build --force`（全パッケージ、生成込み） | **2.7s** |
| `turbo run build`（`oapi-codegen` の初回実行を含む） | 13.4s |

**検証の中身が数秒である一方、`checkout` + `mise install` + `pnpm install` は数十秒かかる。** ジョブを3つに分ければセットアップが3回走り、並列で得た時間を上回る。ジョブ分割が効くのは「1つの検証が数分かかる」規模になってからで、いまではない。

どれが落ちたかは、ステップに `name:` を付けておけば GitHub の画面で分かる。**ジョブを分ける理由が「切り分けやすさ」だけなら、ステップ名で足りる。**

### 5〜6. `--force` — キャッシュヒットは「タスクを実行しない」

turbo のキャッシュヒットは**タスクを実行せず、ログを再生する**。実測で確認した（`cache hit, replaying logs` と表示されるが、`tsp compile` は動いていない）。生成物は `outputs`（`dist/**`）に含まれないため、ヒット時に**作り直しも復元も起きない**。

CI のランナーは毎回まっさらで `.turbo/` を持たないため、今日の構成では必ず miss して実行される。それでも `--force` を付けるのは、**「差分が出なかった」が「作り直した結果、差分が無かった」を必ず意味する状態にするため**である。キャッシュの状態に検証の有効性が依存する形を残さない。

`git status --porcelain` を選んだのは、**追跡外の新規ファイルを拾うため**。`git diff --exit-code` は追跡済みファイルの変更しか見ないので、生成器が新しいファイルを吐いたときの**コミット忘れを見逃す**。1段目の生成（`tsp compile`）は契約の書き方と emitter の設定でファイルが増えうる。

`--porcelain` は終了コードが常に 0 なので、「出力が空であること」を判定する行を自分で書く。

### 7. タグ固定 — [20260812-1324](./20260812-1324-version-pinning-and-audit.md) の目的は「勝手に上がらないこと」

同 ADR が依存を完全固定した目的は、**手を入れていないのに動くものが変わる状態を無くす**ことである。`@v7.0.1` とパッチまで書けばこれは満たされる（`@v7` は上がる）。

コミット SHA まで固定すれば「タグの付け替え」という理論上の穴も塞げるが、代償として**更新のたびに40桁を引いてきて差し替える手間が毎回発生し、バージョンが目で読めなくなる**。週5時間の制約に対して見合わない。公式 action のタグ付け替えは現実的な頻度が低く、起きた場合も本リポジトリは private で攻撃対象になりにくい。

`actions/setup-node` / `setup-go` / `pnpm/action-setup` を併用しないのは、[20260812-1324](./20260812-1324-version-pinning-and-audit.md) と [20260815-1420](./20260815-1420-go-version-and-module-path.md) が既に決めたとおり——**バージョンの情報源が `mise.toml` とワークフローの2箇所に分かれ、片方だけ直しても両方が正常終了してしまう**ため。

### 8. リモートキャッシュを使わない

- **1名・1リポジトリでは共有相手がいない。** リモートキャッシュが効くのは「複数の開発者やランナーが同じハッシュを何度も踏む」場合で、いまはどちらも無い
- 検証の中身が2.7秒である以上、**短縮できる絶対量が小さい**
- 加えて、`--force` を付ける本 ADR の決定と噛み合わない（毎回 bypass するため、そもそも読まれない）
- 外部サービス（Vercel のアカウント連携、または自前のキャッシュサーバー）が1つ増える

### 9. `govulncheck` は 006 に入れない

[20260815-1906](./20260815-1906-lambda-adapter-and-runtime.md) が「`pnpm audit` は Node の依存しか見ない」と正しく指摘している。ただし現在の Go の実行時依存は `aws-lambda-go` と `aws-lambda-go-api-proxy` の2つで、**まだ外部入力を受けて処理する経路が `/healthz` しか無い**。DB アクセス・認証・画像処理が入る v0.1 の投稿機能から、依存も攻撃面も一気に増える。**そこに入る前に別チケットで扱う**のが、費用対効果の山と一致する。

### 10. GitHub Issues に移行しない

[20260812-0905](./20260812-0905-development-workflow.md) が却下理由に挙げた「**ADR と置き場が分かれる**」は、リモートができた今も変わらない。チケットは事前調査・学習TODO・振り返りを含む長文で、**ADR と相互にリンクし合っている**。片方だけを GitHub 側に移すと、リンクがリポジトリの外に出る。

## 却下した案

### public リポジトリ

Actions が無制限に無料で、後から公開する手間も無い。

**却下の理由**: 商標の実査前に名称を露出させる点で、[20260814-1826](./20260814-1826-defer-trademark-research.md) が「不可逆だから取得しない」と決めたドメイン・SNS と同じ性質を持つ。private → public は後からいつでもできるが、**逆は「一度公開された」事実を消せない**。可逆性の高い側を選ぶ。

### `main` へ直接 push する

手数が最小で、ブランチの切り替えもマージも要らない。1人開発なら壊れても自分しか困らない。

**却下の理由**: CI が赤いと分かるのが `main` に入った後になる。`main` からデプロイする以上、`main` が壊れている時間をゼロに近づける仕組みに価値がある。**PR を挟む手数は、チケット1枚（2〜3時間）につき1回**であり、運用の重さとして許容できる。

### 検証ごとにジョブを分ける

並列で速く、どれが落ちたかが一目で分かる。

**却下の理由**: 検証の中身が2.7秒に対し、セットアップ（checkout / mise / pnpm install）が数十秒。**分けた数だけセットアップを繰り返すため、合計時間はむしろ増える。** 切り分けやすさはステップ名で足りる。

### `git diff --exit-code` で判定する

1行で済み、差分の中身がそのままログに出る。

**却下の理由**: **追跡外の新規ファイルを見ない。** 生成器がファイルを増やしたときのコミット忘れを検出できず、「差分が無い＝生成物が最新」が成り立たなくなる。なお `git status --porcelain` を採ったうえで、失敗時に `git diff` を出して中身を見せることは両立する。

### `turbo.jsonc` の `outputs` に生成物（`tsp-output/**` と `internal/rest/gen/**`）を含める

キャッシュヒット時に「そのハッシュに対応する正しい生成物」が復元されるため、キャッシュと差分チェックの噛み合わせの穴が塞がる。005 のステップ10 以降に出るようになった `no output files found for task @repo/api-spec#build` の警告も消える。

**却下の理由**: `--force` を付けることで同じ穴が既に塞がっており、**同じ目的の仕組みを2つ持つことになる**。また `outputs` に生成物を入れると、生成物がキャッシュ経由で復元されるようになり、「コミットされているものが唯一の正」という現在の単純さが1段ぶん複雑になる。**リモートキャッシュを導入するときに再検討する**（下記「結果として必要になる決定」）。

### action をコミット SHA で固定する

タグの付け替えを含めて完全に固定できる。

**却下の理由**: 更新のたびに40桁を差し替える手間が毎回発生し、**バージョンが目で読めなくなる**。得られるのは private リポジトリにおける低確率の攻撃経路を塞ぐことで、週5時間の制約に見合わない。

### 外部の CI サービス（CircleCI など）を使う

**却下の理由**: リポジトリと CI が別サービスになり、連携設定が増える。既存 ADR 2本が `jdx/mise-action`（GitHub Actions 用）を前提にしており、**それを覆すだけの利点が見当たらない**。

### ローカルの git フック（lefthook など）だけで済ませる

CI サービスに依存せず、コミット前に手元で検出できる。速い。

**却下の理由**: **フックは無効化できるし、環境にも依存する。** 「まっさらな環境で通ること」（`node_modules/` も `dist/` も無い状態）を検証できないため、002 で踏んだ種類の壊れ方を構造的に見逃す。なお手元のフックは CI の代替ではなく補完なので、後から足すことは妨げない。

## トレードオフとして受け入れること

- **CI では turbo のキャッシュの利益を捨てる。** `--force` により毎回すべてのタスクが走る。いまは 2.7 秒なので問題にならないが、パッケージが増えれば効いてくる
- **1ジョブなので、どれが落ちてもジョブ全体が赤になる。** 切り分けはステップ名に依存する
- **`no output files found for task @repo/api-spec#build` の警告が出続ける。** `outputs` を直さないため。実害は無いが、CI のログに毎回出るノイズになる
- **タグの付け替えという理論上の穴が残る**
- **Go のモジュールキャッシュ・ビルドキャッシュが効かない。** `actions/setup-go` を使わない選択の代償（[20260815-1420](./20260815-1420-go-version-and-module-path.md)）。必要になったら `actions/cache` で自分で載せる
- **`pnpm audit` が外部要因で CI を落としうる。** 自分のコードを1行も変えなくても、新たに報告された脆弱性で赤くなる（[20260812-1324](./20260812-1324-version-pinning-and-audit.md) が受け入れ済み）
- **Go の依存の脆弱性は、当面チェックされない**（決定9）
- **PR を挟むぶん、チケット1枚につきブランチ作成とマージの手数が増える**
- **private のため Actions は月 2,000 分の枠内で回す。** いまの規模なら十分だが、無制限ではない

## 結果として必要になる決定

- **リモートキャッシュを導入するなら、`outputs` に生成物を含めるかを再検討する**（却下した案を参照）
- **`govulncheck` を CI に足すチケット**（v0.1 の投稿機能に入る前）
- **デプロイ（CD）を CI から流すか、手元から流すか**（チケット 007）。AWS の認証情報を CI に渡すなら OIDC の設定が要る（[20260816-0017](./20260816-0017-infrastructure-as-code-terraform.md) の未決と重なる）
- **Lint / Format（技術選定ガイド G-5）を決めたら CI に足すか**
- **環境分離とシークレット管理（G-7）**
- **ブランチ保護を設定するか**（PR 必須を GitHub 側で強制するか、運用で守るか）
