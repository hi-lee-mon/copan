# Go の内部構成をモジュール単位のレイヤー構造とし、層は中身ができた時点で追加する

- ステータス: 承認
- 日付: 2026-08-15 15:21
- 関連: [20260815-1420 Go のバージョンとモジュールパス](./20260815-1420-go-version-and-module-path.md)、[20260812-0659 バックエンドを Go とする](./20260812-0659-backend-go-openapi-contract.md)、[20260812-0905 開発の進め方](./20260812-0905-development-workflow.md)、[チケット 003](../tickets/003-go-api-skeleton.md)

## コンテキスト

[チケット 003](../tickets/003-go-api-skeleton.md) で `apps/api` に Go のコードを初めて置くにあたり、**`internal/` 配下をどう構成するか**が論点になった。

チケット自体は「`/ping` が 200 を返す」だけを求めており、必要なのは HTTP ハンドラ1つである。しかし v0.1 以降には投稿・店舗・パン種類といった機能と PostgreSQL アクセスが控えており、**そのときに構造を作り直すか、今から見据えた形にするか**を決める必要があった。

制約は次のとおり。

- 開発は**週5時間・1名**。[技術選定ガイド](../tech-decision-guide.md)は「過剰な設計を持ち込まない」ことを求めている
- 一方で [20260812-0905](./20260812-0905-development-workflow.md) は**学習をプロダクト完成と並ぶ目的**に据えている。設計はその学習対象そのものである
- **B-3 / B-4（Go の DB アクセスとマイグレーション管理）が未決。** CLAUDE.md が「ORM ではなく sqlc で生 SQL」と定めているだけで、sqlc の生成コードと repository インターフェースをどう噛み合わせるかは決まっていない
- 004〜005 で **TypeSpec から生成したコードが HTTP 層に入ってくる**

## 決定

### 1. 目指す構造（機能モジュール単位のレイヤー分割）

```text
apps/api/internal/{module}/
├── domain/
│   ├── model/               # エンティティ・値オブジェクト
│   └── repository/          # 永続化の抽象。Reader / Writer に分離する
├── usecase/
│   ├── port/
│   │   └── output/          # Output Port（複数の usecase で共有する interface のみ残す）
│   └── interactor.go        # struct として公開する
├── interface/
│   └── rest/handler/        # HTTP 層。依存する interface は利用側（この層）で定義する
└── infrastructure/
    └── postgres/            # repository の実装
```

`{module}` は**機能単位**（`health` / 今後の `post`・`shop` 等）とする。

### 2. 層は「中身ができた時点」で追加する。空のディレクトリを先に作らない

003 の時点で実体化するのは **HTTP ハンドラ層のみ**。

```text
apps/api/internal/health/
└── interface/rest/handler/
    ├── ping.go
    └── ping_test.go
```

`domain/` は DB 設計時、`infrastructure/postgres/` は B-3 / B-4 の確定後、`usecase/` は中身のあるユースケースが現れた時点で追加する。

### 3. テストは外部テストパッケージ（`package xxx_test`）を既定とする

テストファイルは対象と同じディレクトリに置き（Go の規約）、`package` 行を `xxx_test` にする。非公開の細部を直接検証したい特別な理由があるときだけ、内部テストパッケージ（`package xxx`）を使う。

## 理由

### 目指す構造をレイヤー分割にした理由

- **学習が目的の一つである。** [20260812-0905](./20260812-0905-development-workflow.md) は「本人がその仕組みを自分の言葉で説明できるようになること」を目的に据えており、設計はその中心にある。Go は本人が業務で使う言語で学習対象ではないが、**設計は学習対象**だと同 ADR が整理している
- **`interface/rest/handler` という境界が 004〜005 と噛み合う。** TypeSpec から生成されるのは「実装すべきメソッドの集合」と「それを HTTP に紐づけるルーター」で、ちょうどこの層に落ちる。生成物と手書きの境目が構造上はっきりする
- **「利用側で interface を定義する」方針が Go の慣習に沿っている。** Go では *"Accept interfaces, return structs"* が定着しており、インターフェースは実装側ではなく**それを必要とする側のパッケージ**に置く。Java 由来の Clean Architecture 実装にありがちな「実装側に interface を置く」形より、言語の粒度に合っている
- **`repository` を Reader / Writer に分離**すると、usecase が必要な操作にだけ依存できる

### 空のディレクトリを先に作らない理由

- **Git は空ディレクトリを記録できない。** フル構造を今作ると、`.gitkeep` のようなダミーファイルを4つ置くか、ディレクトリが消えるかのどちらかになる
- **未決の決定を前提に形だけ置くことになる。** `infrastructure/postgres/` は B-3 / B-4 が決まっていない状態では中身の設計ができず、決まった時点で作り直す可能性が高い
- **`/ping` には domain も usecase も存在しない。** ヘルスチェックにビジネスロジックは無く、通しても中身の無い層を経由するだけになる
- 構造の全体像は**この ADR が持つ**。コードから読み取れなくても、記録が残っていれば意図は失われない

### `/ping` を `internal/health/` に置いた理由

ヘルスチェックは横断的関心事で、`post` や `shop` のような機能モジュールのどれにも属さない。**それ自体を一つのモジュールとして扱う**ことで、構造の一貫性を保つ。004 で `/health` に差し替えるときも置き場所がそのまま使える。

### 外部テストパッケージを既定にした理由

- **公開されているものしか触れないため、利用者と同じ目線でテストを書くことになる。** TDD で「振る舞いを先に決める」やり方と相性がよい
- 内部実装を変えてもテストが壊れにくく、リファクタの安全網として機能する
- なお **co-location（テストを対象と同じディレクトリに置く）は Go では選択肢ではなく規約**であり、この決定とは無関係にどちらでも満たされる。外部テストパッケージは「別ディレクトリに置く」意味ではなく、同じディレクトリのままコンパイル単位だけを分ける仕組みである

## 却下した案

### 003 でフル構造のディレクトリを作る

全体像が常にコード上に見える利点がある。

**却下の理由**: 4つのディレクトリが空になり、`.gitkeep` が必要になる。加えて `infrastructure/postgres` は未決の B-3 / B-4 を前提に形だけ置くことになり、決まった時点で作り直す可能性が高い。**得られるのは「見える」ことだけで、それは ADR で代替できる。**

### 003 で usecase まで通す

`/ping` でも handler → interactor を経由させ、レイヤー間の受け渡しを一度体験する案。学習目的としては意味がある。

**却下の理由**: ヘルスチェックにビジネスロジックが存在しないため、**中身の無い層を通すだけ**になる。「レイヤーを通す体験」は、実際に中身のあるユースケース（v0.1 の投稿機能）で行うほうが学習として正確。空の層を通す形を先に作ると、それが手本として残ってしまう。

### `internal/handler` の1パッケージにまとめる

エンドポイントが1つしかない現段階では最小の手数。分割は必要になってから行う。

**却下の理由**: 目指す構造が決まっているなら、後から全体を動かすより最初からその位置に置くほうが安い。またこの案は「設計を学ぶ」という目的を先送りにする。

### `internal/server`（組み立て）+ `internal/handler`（個別）の2層

レイヤー構造より軽く、ルーター組み立てとハンドラの分離だけを行う案。

**却下の理由**: 機能が増えたときにモジュール単位の凝集が失われる。`handler/` に全機能のハンドラが平積みになる形は、v0.1 の機能数でも早々に見通しが悪くなる。

## トレードオフとして受け入れること

- **階層が深い。** `/ping` のような単純なエンドポイントでも `internal/health/interface/rest/handler/` まで降りることになる。1名・週5時間という制約に対して、ファイルを開くまでの距離が長い
- **`interface` はディレクトリ名にはできても、パッケージ名にはできない。** `interface` は Go のキーワードであり `package interface` は構文エラーになる。中間ディレクトリとして通過する分には問題ないが、**`interface/` 直下に共通コードを置きたくなった時点で名前を変えることになる**（Go の実装で `adapter/` や `transport/` が使われるのはこれが理由）
- **構造の全体像がコードから読み取れない。** 空の層を作らないため、この ADR を読まないと目指す形が分からない
- **モジュールの切り方が今後の判断に残る。** `health` は明快だが、`post` と `shop` の境界などは v0.1 の設計時に決めることになる

## 結果として必要になる決定

- **ルーターの組み立てをどこに置くか。** 各モジュールのハンドラを集めて1つの `http.Handler` にする役が必要になる。モジュールの外（`internal/rest/router.go` 等）に置くことになるが、004 で TypeSpec の生成コードが入る形と併せて決める（チケット 003 のステップ8、または 005）
- **repository のインターフェースを `domain/repository` と `usecase/port/output` のどちらに置くか。** 目指す構造には両方が登場しており、使い分けの基準が未定（DB 設計時）
- **B-3 / B-4 — sqlc の生成コードと `infrastructure/postgres` の噛み合わせ**（DB 設計時）
- **`interface/` の名前を維持するか。** 上記の制約に当たった時点で判断する
