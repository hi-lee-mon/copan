# HTTP ルーターの組み立てを `internal/rest` に置き、各モジュールはハンドラ関数だけを公開する

- ステータス: 承認
- 日付: 2026-08-15 23:15
- 関連: [20260815-1521 Go の内部構成](./20260815-1521-go-layered-architecture.md)、[20260815-1548 ルーターは標準の ServeMux](./20260815-1548-router-stdlib-servemux.md)、[20260812-0659 バックエンドを Go とする](./20260812-0659-backend-go-openapi-contract.md)、[チケット 003](../tickets/003-go-api-skeleton.md)

## コンテキスト

[20260815-1521](./20260815-1521-go-layered-architecture.md):119 が「**ルーターの組み立てをどこに置くか**」を宿題として残していた。

> 各モジュールのハンドラを集めて1つの `http.Handler` にする役が必要になる。モジュールの外（`internal/rest/router.go` 等）に置くことになるが、004 で TypeSpec の生成コードが入る形と併せて決める（チケット 003 のステップ8、または 005）

チケット 003 のステップ5までの実装では、`NewRouter()` が `internal/health/interface/rest/handler` に置かれていた。**`health` モジュールの中に、アプリ全体のルーティングがある**状態である。このまま `store` / `post` が増えると、`health` のパッケージに無関係なルートを書き足すことになる。

制約は次のとおり。

- **[20260815-1521](./20260815-1521-go-layered-architecture.md) の構造は決定済み。** `internal/{module}/` のレイヤー分割を維持する
- **004〜005 で TypeSpec の生成コードが HTTP 層に入る。** 一般的な OpenAPI コードジェネレータは「実装すべきメソッドの集合」と「それを `http.ServeMux` に紐づけるルーター」を生成する。すなわち**ルーティングの登録処理そのものが生成物に置き換わる可能性が高い**
- **Go は循環インポートをコンパイルエラーにする。** 「ルーターがモジュールを知る」か「モジュールがルーターを知る」かのどちらか一方に決める必要がある
- CLAUDE.md は「**API 契約の単一情報源は TypeSpec**」と定めている

## 決定

### 1. ルーターの組み立ては `internal/rest/router.go`（`package rest`）に置く

```go
package rest

func NewRouter() http.Handler {
	mux := http.NewServeMux()

	mux.HandleFunc("GET /ping", handler.Ping)

	return mux
}
```

### 2. 各モジュールはパスを知らず、ハンドラ関数だけを公開する

```text
apps/api/internal/
├── rest/
│   └── router.go                        package rest    ← ルーティングの知識はここだけ
└── health/
    └── interface/rest/handler/
        └── ping.go                      package handler ← func Ping(w, r) を公開
```

`handler.Ping` は**大文字**で公開する。`rest` パッケージから呼ぶため、Go の可視性規則（先頭が大文字なら公開）上こうなる。

### 3. 依存の向きは `rest` → 各モジュールの一方通行とする

モジュール側は `rest` を import しない。

### 4. `cmd/local` と `cmd/lambda` は `rest.NewRouter()` を呼ぶ

両者が同じ `http.Handler` を受け取る形を維持する（チケット 003 の完了条件「実装が二重になっていない」）。

## 理由

- **[20260815-1521](./20260815-1521-go-layered-architecture.md):119 が示した方向にそのまま従う。** 「モジュールの外（`internal/rest/router.go` 等）」と例示されており、本 ADR はそれを確定させただけである
- **004 の差し替え範囲が1ファイルに収まる。** 生成コードがルーティングを持つ形になっても、書き換えるのは `internal/rest/router.go` だけで済む。各モジュールのハンドラ関数はそのまま生かせる
- **パスの知識が1箇所に集まる。** CLAUDE.md の「API 契約の単一情報源は TypeSpec」に照らすと、パスは最終的に TypeSpec が持つ。手書きの間も1箇所に集約しておけば、生成物に移すときの対応が明確になる
- **依存の向きが自然。** ルーターは全モジュールを知る必要があり、モジュールはルーターを知る必要がない。Go は循環インポートを許さないため、この向きを最初に固定しておく価値がある

## 却下した案

### 各モジュールが `Routes(mux *http.ServeMux)` を公開し、自分のルートを自分で登録する

```go
// internal/health/... で
func Routes(mux *http.ServeMux) { mux.HandleFunc("GET /ping", ping) }
```

モジュールの自律性が高く、ハンドラ関数を非公開（小文字）に保てる利点がある。

**却下の理由**: **パスの知識が各モジュールに散る。** 004 で生成コードがルーティングを持つ形になったとき、全モジュールに手を入れることになる。「API 契約の単一情報源は TypeSpec」という制約とも向きが逆で、パスがコード側に分散した状態を作る。

### `NewRouter()` を `internal/health/...` に置いたままにする

現状維持。ファイルを動かさずに済む。

**却下の理由**: `store` / `post` が増えるたびに、`health` モジュールの中に無関係なルートを書き足すことになる。[20260815-1521](./20260815-1521-go-layered-architecture.md) がモジュール単位の凝集を目的に据えている以上、その目的に正面から反する。

### `internal/` をフラットにし、1モジュール = 1パッケージにする

`internal/api/router.go` と `internal/health/health.go` の2ファイルに畳む案。Go では「1ドメイン = 1パッケージ、その中をレイヤーで割らない」が主流の粒度であり、標準ライブラリ自身（`net/http` にサーバーもクライアントもハンドラも同居する）がその形である。加えて **Go の可視性はパッケージ単位**であるため、レイヤーごとにパッケージを割ると、本来隠したい関数を公開せざるを得なくなる（`handler` から `usecase` を呼ぶために `usecase` 側を大文字にする必要が生じる）。

**却下の理由**: [20260815-1521](./20260815-1521-go-layered-architecture.md) が「`internal/server` + `internal/handler` の2層」および「`internal/handler` の1パッケージ」として**既に検討し却下している**。同 ADR は階層の深さ（:112）と `interface` がパッケージ名にできないこと（:113）を認識した上でレイヤー構造を選んでおり、学習を目的の一つに据える [20260812-0905](./20260812-0905-development-workflow.md) を根拠にしている。

**「可視性がパッケージ単位である」点は同 ADR に記載が無く、新しい論点ではある。** ただしこの害が顕在化するのは `domain` / `usecase` / `infrastructure` を実体化してパッケージが実際に割れたときであり、現時点では `interface/rest/handler` が1パッケージしか存在しないため発生しない。**構造の再検討はその時点に回す。** 決定済みの ADR を、まだ効いていない論点で覆すことはしない。

## トレードオフとして受け入れること

- **`rest` という語が2箇所に現れる。** `internal/rest/`（パッケージ名 `rest`）と `internal/{module}/interface/rest/`（ディレクトリ名）。パッケージ名は `rest` と `handler` で異なるため衝突はしないが、読み手が混乱する余地がある。[20260815-1521](./20260815-1521-go-layered-architecture.md):122 が「`interface/` の名前を維持するか」を宿題に残しており、そのときに併せて見直す
- **モジュールが増えるたびに `router.go` を触る。** ルーターが全モジュールを import するため、追加のたびに1ファイルが変更点になる。逆に言えば「どのパスが存在するか」がこのファイルを見れば分かる
- **`internal/rest` はモジュールではない。** [20260815-1521](./20260815-1521-go-layered-architecture.md) の `internal/{module}/` という規則の外にある例外的なパッケージになる。同じ性質のもの（今後のミドルウェア等）が増えると、モジュールと非モジュールの区別を意識する必要が出る

## 結果として必要になる決定

- **004 で生成コードが入ったとき、`NewRouter()` がどう変わるか**（生成物がルーターを持つなら、この関数は生成コードを呼ぶだけになる）
- **ミドルウェア（ログ・パニックリカバリ・CORS）をどこに挟むか**（必要になった時点。`internal/rest` に置くか別パッケージにするか）
- **`internal/rest` 以外の非モジュールなパッケージが増えたときの置き場所の規則**
