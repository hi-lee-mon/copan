# モノレポのディレクトリ構成を apps/ + packages/ の2系統とし、パッケージ名を `@repo/*` で揃える

- ステータス: 承認
- 日付: 2026-08-12 13:13
- 関連: [20260811-2015 モノレポ構成に Turborepo を採用する](./20260811-2015-monorepo-turborepo.md)、[20260812-1305 Go を Turborepo 公式の多言語パターンでワークスペースに含める](./20260812-1305-go-in-turborepo-workspace.md)、[20260812-1309 パッケージマネージャに pnpm を採用する](./20260812-1309-package-manager-pnpm.md)、[チケット 002](../tickets/002-monorepo-scaffold.md)

## コンテキスト

[20260811-2015](./20260811-2015-monorepo-turborepo.md) の「結果として必要になる決定」に**ディレクトリ構成（`apps/` と `packages/` の切り方）**が残っていた。同ADRは書き換えず、本ADRで確定させる。

決めるべき論点は3つあった。

1. **Go の API をどこに置くか** — Turborepo の一般構成ガイドは「`apps/` にアプリケーションとサービス、`packages/` にライブラリ」とする。一方、[多言語ガイド](https://turborepo.dev/docs/guides/multi-language)の Go の例は `services/api` に置いている
2. **パッケージ名の付け方** — スコープを使うか、使うなら何にするか
3. **`packages/` の粒度** — TypeSpec の定義と、そこから生成される TS の型を、同じパッケージにするか分けるか

制約として、Turborepo のワークスペース定義は **`apps/**` のようなネストしたグロブを解釈しない**（`apps/*` の1階層まで）。

## 決定

### 1. ディレクトリは `apps/` と `packages/` の2系統

```text
copan/
├── apps/
│   ├── web/          # Next.js
│   └── api/          # Go
├── packages/
│   ├── api-spec/     # TypeSpec の定義（手で書く）
│   └── api-client/   # 生成された TS の型・APIクライアント（コミットする）
├── package.json
├── turbo.json
└── pnpm-workspace.yaml
```

`pnpm-workspace.yaml` に列挙するのは `apps/*` と `packages/*` の2行のみ。

### 2. パッケージ名は `@repo/*`

| ディレクトリ | `package.json` の `name` |
| --- | --- |
| `apps/web` | `@repo/web` |
| `apps/api` | `@repo/api` |
| `packages/api-spec` | `@repo/api-spec` |
| `packages/api-client` | `@repo/api-client` |

### 3. `packages/` は定義と生成物を分ける

`packages/api-spec`（TypeSpec の定義）から `packages/api-client`（生成された TS）を作り、`apps/web` がそれを参照する。ビルド順序は `dependsOn: ["^build"]` に乗せる。

```text
api-spec → api-client → web
```

**ただし中身は空のディレクトリと `package.json` だけに留める。** 生成タスクの具体は、TypeSpec に実際に触れるチケット 004 で確定させる。

## 理由

### `services/api` ではなく `apps/api` を選んだ理由

- **`web` と `api` は「単独でデプロイされるもの」という同じ性質**を持つ。ディレクトリ系統を分ける根拠は、言語が違うことだけになる
- ディレクトリ系統を3つに増やすと、`pnpm-workspace.yaml`・`turbo.json` のフィルタ・CI のパス指定のすべてで3行書くことになる。1人・週5時間の規模では、得られる区別に見合わない
- 公式の多言語ガイドが `services/` を使っているのは、**多言語であることを説明するための例**であって推奨構成ではない。[20260812-1305](./20260812-1305-go-in-turborepo-workspace.md) の「公式パターンから逸脱しない」は `package.json` でパッケージ境界を作るという**手段**についての決定であり、ディレクトリ名はその対象外

### `@copan/*` ではなく `@repo/*` を選んだ理由

- **プロダクト名がまだ確定していない。** [チケット 001](../tickets/001-trademark-domain-research.md)（商標の実査）が進行中で、「コパン／COPAN」を変更する可能性が残っている。`@copan/*` にすると、名称変更時に全パッケージの `name` と、それを参照するすべての `dependencies` を書き換えることになる
- 公式ドキュメントとテンプレートが `@repo/*` を使っているため、**ドキュメントのコード例をそのまま写せる**
- npm に公開しないため、スコープ名が何であれ外部との衝突は起きない

### 定義と生成物のパッケージを分けた理由

- **`apps/web` に TypeSpec のツールチェーンを持ち込まずに済む。** web が依存するのは生成された TS の型だけで、コンパイラは不要
- [CLAUDE.md の制約](../../CLAUDE.md)「生成物はコミットし、CI で再生成して差分が出たら失敗させる」に対し、**差分チェックの対象が `packages/api-client` の1つに閉じる**。同居させると「手で書いた定義」と「生成物」が同じパッケージ内に混ざり、チェック対象をパスで絞ることになる
- Turborepo のキャッシュ粒度が細かくなる。定義を変えていなければ生成タスクがスキップされる

## 却下した案

### `services/api` に Go を置く

言語・ツールチェーンの違いがディレクトリ名で一目で分かる。

**却下の理由**: 上記のとおり、区別して得られるものが「見た目の分かりやすさ」に留まる一方、ワークスペース定義・タスクのフィルタ・CI のパス指定が恒久的に1系統ぶん増える。なお `apps/api` にも `package.json` と `turbo.json` を置くため、[20260812-1305](./20260812-1305-go-in-turborepo-workspace.md) の決定はディレクトリ名によらず成立する。

### パッケージ名を `@copan/*` にする

ログやエラー出力でどのプロダクトのものか即座に分かる。

**却下の理由**: 商標の実査（チケット 001）が未完了で、プロダクト名が変わりうる。**1リポジトリ・1プロダクトである以上、ログでプロダクトを区別する必要がそもそも無い。** 名称確定後に `@copan/*` へ改名することは可能だが、その利益は上記のとおり小さい。

### パッケージ名をスコープなし（`web`、`api`）にする

短く、タイプ量が減る。

**却下の理由**: `api` のような一般的な名前は、将来 npm の外部パッケージと名前が衝突しうる。スコープを付けておけば内部パッケージであることが名前から自明になる。

### `packages/api-contract` に定義と生成物をまとめる

パッケージ数が減り、定義と生成物が常にセットで動く。

**却下の理由**: `apps/web` が TypeSpec のツールチェーンを間接的に引き込む。また、CI での生成物の差分チェックが「パッケージ単位」ではなく「パッケージ内の特定ディレクトリ単位」になり、[20260812-1309](./20260812-1309-package-manager-pnpm.md) で pnpm を選んだ動機（依存関係を宣言で明示する）と噛み合わない。

### `packages/` の決定をチケット 004 まで保留する

TypeSpec に実際に触れてから決めたほうが精度が上がる。

**却下の理由**: 名前と粒度だけなら今決められ、決めておけば `pnpm-workspace.yaml` と `turbo.json` を 002 で完成させられる。**中身（生成タスクの定義、出力パス、生成コマンド）は 004 に持ち越す**ことで、精度の懸念には対処できている。

## トレードオフとして受け入れること

- **`apps/` に言語の違うものが混在する。** `apps/` 配下を一律に扱うスクリプト（例: 全部に `pnpm install` を期待する類）を書くと `apps/api` で破綻する。パッケージごとの `package.json` の `scripts` を通す規律で対処する
- **`@repo/*` はプロダクト名を表さない。** 将来 `@copan/*` に改名する場合、全パッケージの `name` と参照箇所を書き換える作業が発生する。その時点で新しい ADR を書く
- **パッケージが2つ増える。** `packages/api-spec` と `packages/api-client` はどちらも小さく、`package.json` の保守対象が増える

## 結果として必要になる決定

- **Node.js と pnpm のバージョン固定方法**（チケット 002 の残TODO）
- Go のビルド成果物の出力先と、`apps/api/turbo.json` の `outputs` に書くパス。Lambda 向けのバイナリ名の制約と併せて決める（チケット 003 / 007）
- `packages/api-spec` の生成タスク名と、`packages/api-client` の `outputs`（チケット 004）
- `apps/web` の `devDependencies` に `@repo/api` を書くか（Go のビルドを web より先に走らせる必要が実際にあるかで決まる。現時点では不要の可能性が高い）
