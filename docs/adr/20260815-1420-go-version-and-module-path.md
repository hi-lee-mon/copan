# Go のバージョンを `mise.toml` で 1.26.6 に固定し、モジュールパスを `github.com/hi-lee-mon/copan/apps/api` とする

- ステータス: 承認
- 日付: 2026-08-15 14:20
- 関連: [20260812-1324 バージョン固定と audit](./20260812-1324-version-pinning-and-audit.md)、[20260812-1305 Go を Turborepo に含める](./20260812-1305-go-in-turborepo-workspace.md)、[20260812-0659 バックエンドを Go とする](./20260812-0659-backend-go-openapi-contract.md)、[20260814-1826 商標の実査を繰り延べる](./20260814-1826-defer-trademark-research.md)、[チケット 003](../tickets/003-go-api-skeleton.md)

## コンテキスト

[20260812-1324](./20260812-1324-version-pinning-and-audit.md) は Node.js と pnpm のバージョンを `mise.toml` に集約したが、**Go のバージョンは「結果として必要になる決定」として宿題に残していた**。チケット 003 で Go のコードを初めて置くにあたり、次の2点を同時に決める必要が出た。

1. **Go のバージョン** — どれに固定し、`mise.toml` に含めるか
2. **モジュールパス** — `go.mod` の `module` 行に何を書くか

### 1 の制約

- 開発マシンのグローバル設定（`~/.config/mise/config.toml`）は Go 1.25.1
- mise から取得可能なのは 1.24.10 〜 **1.26.6**（1.26.6 が最新）
- Lambda の `provided.al2023` ランタイムは**静的リンクされたバイナリを実行するだけ**であり、Go のバージョンに制約を課さない
- `go.mod` の `go` ディレクティブは Go 1.21 以降 **強制**（手元の Go がこれより古いとビルドが拒否される）になっており、`toolchain` ディレクティブによる自動ダウンロードと合わせて、「mise が入れる Go 本体」と「`go.mod` が要求する Go」の2箇所が存在する

### 2 の制約

- **このリポジトリにはまだ git のリモートが無い**（`git remote` が空）
- 名称は [20260814-1826](./20260814-1826-defer-trademark-research.md) により、v0.1 の間は「**仮の COPAN**」として扱う。**ドメインと SNS アカウントは不可逆なので取得しない**方針
- したがって「モジュールパスも名称確定を待つべきか」が論点になった

## 決定

### 1. Go のバージョンは 1.26.6。`mise.toml` に含める

```toml
# mise.toml
[tools]
node = "24.19.0"
pnpm = "11.21.0"
go = "1.26.6"
```

`go.mod` の `go` ディレクティブは、**`go mod init` が書き込んだ既定値 `go 1.26.6` をそのまま使う**（パッチ番号まで書く）。手で書き換えない。

- `mise.toml` = 「開発機と CI で**実際に使う**Go」を固定する
- `go.mod` の `go` = 「このモジュールが**要求する最低**バージョン」かつ「使う言語仕様のバージョン」

役割は違うが、**両者を同じ値に揃える**。Go を上げるときは2箇所とも更新する（後述「トレードオフ」）。

### 2. モジュールパスは `github.com/hi-lee-mon/copan/apps/api`

```go
// apps/api/go.mod
module github.com/hi-lee-mon/copan/apps/api

go 1.26.0
```

**名称の確定を待たない。** リモート未設定のまま、この値で先行する。

## 理由

### バージョンを 1.26.6 にした理由

- **パッチが6まで出ており枯れている。** 最新マイナーだからという理由での回避は当たらない
- **Lambda 側に制約が無い。** `provided.al2023` は静的バイナリを実行するだけで、ランタイム側の Go バージョンという概念がそもそも存在しない。「デプロイ先に合わせて古いバージョンを選ぶ」必要がない
- **1.25.1 に揃える案は [20260812-1324](./20260812-1324-version-pinning-and-audit.md) の方針と衝突する。** 同 ADR は「依存を完全固定して CI で `pnpm audit` を強制する」——つまり**既知の脆弱性を放置しない**ことを決めている。1.25 系はその後12パッチ出ており、セキュリティ修正が未適用の状態を選ぶ理由がない
- **ローカルのグローバル設定（1.25.1）と食い違っても問題にならない。** mise はプロジェクト内の `mise.toml` をグローバル設定より優先する。他プロジェクトへの影響も無い

### `mise.toml` に含めた理由

[20260812-1324](./20260812-1324-version-pinning-and-audit.md) が既に述べているとおり、**開発マシンでは mise が Go を管理済み**であり、1行足すだけで済む。`devEngines`（`package.json` 上のバージョン宣言）は JS エコシステム専用のため Go には使えず、代替がない。

CI（チケット 006）の Go セットアップも `jdx/mise-action` に寄ることになる。`actions/setup-go` を併用するとバージョンの真実が2箇所に分かれるため、これは避ける。

### `go.mod` を `go mod init` の既定値のままにした理由

Go 1.21 以降、`go mod init` は `go` ディレクティブに**パッチまで含めた現在のツールチェーンのバージョンを書き込む**。これが公式の既定動作である。

当初は「`go` ディレクティブは最低要求バージョンなのだから、パッチまで書くのは要求として強すぎる」として `go 1.26.0` に手で直す案を検討したが、**却下した**（下記）。[20260812-1305](./20260812-1305-go-in-turborepo-workspace.md) で「**公式パターンが存在する以上それを正とし、独自の工夫を持ち込まない**」と決めている以上、既定値を手で書き換える行為はその方針に反する。

補足として、`go` ディレクティブのうち**言語仕様のバージョンを決めるのはマイナーまで**であり、パッチ部分は最低要求バージョンの判定にしか使われない。すなわち `1.26.0` と `1.26.6` でコンパイル結果は変わらず、差が出るのは「1.26.6 未満の Go で叩いたとき」だけである。本プロジェクトでは開発者1名・CI とも `mise.toml` 経由で 1.26.6 を使うため、**その状況が発生しない。**

### モジュールパスを URL 形式にした理由

- **可逆である。** [20260814-1826](./20260814-1826-defer-trademark-research.md) が名称確定を待たせているのは**ドメインと SNS アカウントが不可逆**だからであり、その論理は `go.mod` には及ばない。GitHub のリポジトリ名は改名でき、`go.mod` は書き換えられる
- **リモートが無くても動く。** Go はモジュールパスと実際の取得先の一致を、そのモジュール自身をビルドする際には検証しない。検証が走るのは**他のモジュールがこれを `go get` するとき**であり、このモジュールは実行バイナリであって配布物ではない
- **慣例に乗ることのコストがゼロ。** 逸脱しても得るものが無い

## 却下した案

### バージョン: 1.25.13（1つ前のマイナーの最新パッチ）

グローバル設定 1.25.1 と同じマイナー系列に揃える保守的な案。

**却下の理由**: 揃える相手（グローバル設定）自体に根拠が無い。単に以前入れたまま更新していない値であり、それを基準にするのは理由として弱い。また mise がプロジェクト単位でバージョンを切り替える以上、揃えることの実利も無い。

### バージョン: 1.25.1（ローカルのグローバル設定に合わせる）

既にインストール済みでダウンロードが不要、という利点のみ。

**却下の理由**: セキュリティ修正が12パッチ分未適用になる。[20260812-1324](./20260812-1324-version-pinning-and-audit.md) の脆弱性チェック方針と整合しない。ダウンロード1回分の時間は判断材料として小さすぎる。

### `go.mod` の `go` を `1.26.0` に手で直す

`go` ディレクティブは「最低要求バージョン」であり、実際に使うパッチの固定は `mise.toml` の仕事だから役割を分けるべき、という案。パッチまで書くと「1.26.5 では一切ビルドできない」という強い要求になる点を問題視した。

**却下の理由**: 得られる利益がこのプロジェクトでは**ゼロ**である。1.26.6 未満の環境が存在しない（開発者1名、CI も `mise.toml` を読む）ため、要求が強いことによる被害者がいない。一方で失うものが「公式ツールの既定値からの逸脱」であり、[20260812-1305](./20260812-1305-go-in-turborepo-workspace.md) の方針に正面から反する。**一般論としては正しい整理でも、この文脈では独自の工夫にしかならない。**

### モジュールパス: `copan/apps/api`（URL 形式にしない）

外部配布しないのだから住所は不要、という割り切り。ドット（`.`）を含まないパスは Go がリモートと解釈しないため、`go get` の対象外になる。

**却下の理由**: 得るものが「GitHub ユーザー名を書かずに済む」だけで、失うものが「将来ライブラリとして切り出す／他モジュールから参照する際に書き換えが必要になる」「他の Go プロジェクトと見た目が違う」。**トレードオフが一方的に不利。**

### モジュールパス: 名称が確定するまで決めない

**却下の理由**: チケット 003 が丸ごと止まる。止めてまで守る不可逆性がここには無い（上記「理由」参照）。[20260814-1826](./20260814-1826-defer-trademark-research.md) の趣旨は「不可逆な取得を先送りする」ことであって、「名称に触れる作業を全部止める」ことではない。

## トレードオフとして受け入れること

- **モジュールパスと実際のリモートが一致しない期間がある。** GitHub リポジトリを `hi-lee-mon/copan` 以外の名前で作った場合、`go.mod` の書き換えが必要になる。書き換えは `go.mod` 1行と import 文の一括置換で済む
- **名称変更時に `go.mod` と全 import 文の変更が発生する。** 商標の実査（001 の残り）の結果しだいで起きる。機械的な置換で済むが、diff は広く出る
- **`mise.toml` と `go.mod` にバージョンが2箇所書かれる。Go を上げるときは両方を更新する。** 片方だけ上げても壊れないため（`mise.toml` を 1.26.7 にしても `go 1.26.6` の要求は満たされる）、**`go.mod` が放置されて実態とズレる**経路がある。壊れないズレなので実害は小さいが、運用ルールとして両方を触ることにする
- **`go.mod` を `mise.toml` より新しい値にしてはいけない。** Go 1.21 で入った `GOTOOLCHAIN`（既定値 `auto`）は、`go.mod` の要求が手元の Go より新しい場合に**必要なツールチェーンを自分でダウンロードして使う**。これは mise の管理外（`~/.cache/go/toolchain`）で起き、[20260812-1324](./20260812-1324-version-pinning-and-audit.md) の「バージョンの真実は `mise.toml` に集約する」という前提が静かに破れる。**Go を下げるときは `go.mod` を先に下げる**
- **Go 1.26 系に固有の問題が出た場合、退避先が 1.25 系になる。** その場合は `go.mod` の `go` ディレクティブも下げる必要がある（上記の順序に注意）

## 結果として必要になる決定

- **Lambda アダプタを自前で書くか、既存ライブラリ（`aws-lambda-go-api-proxy` 等）を使うか**（チケット 003）
- **Lambda のランタイムとバイナリ名の規約**（`provided.al2023` / `bootstrap`）（チケット 003）
- **`apps/api` の turbo タスク設定** — ビルド成果物の出力先と `outputs` の指定、`test` タスクのキャッシュ方針（チケット 003）
- **CI での Go セットアップを `jdx/mise-action` に寄せる**（チケット 006）
- Go のマイナーバージョンを上げる契機と手順（当面は必要になった時点で判断する）
