# データベースは Neon で開始し、v1.0公開前に東京リージョンのPostgresへ移行する

- ステータス: 承認
- 日付: 2026-08-12 08:05
- 関連: [インフラ構成](./20260812-0712-infrastructure-cloudflare-aws-hybrid.md)（本ADRはそのデータ層の選定を更新する）、[Go採用](./20260812-0659-backend-go-openapi-contract.md)

## コンテキスト

[インフラ構成のADR](./20260812-0712-infrastructure-cloudflare-aws-hybrid.md)でデータ層に Neon を採用したが、その後の調査で **Neon に東京リージョンが存在しない**ことが判明した。

Neon がサポートする AWS リージョンは8つ（バージニア北部 / オハイオ / オレゴン / フランクフルト / ロンドン / **シンガポール** / シドニー / サンパウロ）で、**アジアはシンガポールとシドニーのみ**である。Azure リージョンは非推奨となり新規作成できない。

東京〜シンガポール間の往復はおおよそ **70ms前後**（正確な値は実測が必要）。この遅延は、APIとDBの配置によって影響の出方が変わる。

| 配置 | ユーザー→API | API→DB | 実質的な遅延 |
| --- | --- | --- | --- |
| Lambda東京 + DBシンガポール | 速い | 70ms × クエリ回数 | クエリ2回で +140ms |
| Lambda・DB 両方シンガポール | +70ms | 速い | +70ms（固定） |
| Lambda・DB 両方東京 | 速い | 速い | ほぼゼロ |

COPANは「街を歩いていてサッと開く」体験を中核に据えているため、この遅延は無視できない。

あわせて「Cloudflare で完結できないか（D1）」の再検証と、東京リージョンで PostGIS が使えるサービスの調査を行った。

## 決定

1. **v0.1（自分専用）は Neon（シンガポール・無料枠）で開始する。**
2. **v1.0（一般公開）の前に、東京リージョンの PostgreSQL へ移行する。**
3. 移行先の第一候補は **PlanetScale Postgres**（東京・月$5）、代替は **Supabase**（東京・月$25）。
4. **移行可能性を保つための制約を、開発の最初から設計に課す**（後述）。

## 理由

### なぜ v0.1 は Neon のままでよいのか

**v0.1 は自分専用であり、ユーザーが1人だからである。** レイテンシが実害を生むのは一般公開後であって、シードデータを作る段階では問題にならない。

そしてこの段階では Neon の無料枠で完全に賄える。**「遅延が問題になる時期」と「移行すべき時期」が一致している**ため、リリース計画（v0.1 → v1.0）の区切りをそのまま移行の区切りとして使える。

### なぜ移行先を今すぐ確定しないのか

第一候補である PlanetScale Postgres は、**東京リージョンがあり単一ノードで月$5**（本番向け3ノードHA構成でも月$15、ストレージ10GB込み）と、条件を満たすサービスの中で最も安い。

しかし **2026年8月時点で、運用上の問題により PostGIS 関連の拡張（postgis / postgis_topology / postgis_sfcgal 等）が一時的に無効化されている**（公式ドキュメントに復旧予定と記載）。

この不確実性は、**移行を実施する時点まで判断を先送りできる**。今決める必要がない。

### なぜ移行先の候補を2つ持つのか

PlanetScale の PostGIS が復旧しなかった場合に詰まらないようにするため。Supabase（東京・PostGIS公式サポート・認証機能込み）を退避先として確保しておく。

## 移行可能性を保つために課す制約

**この制約は、v0.1 の実装開始時点から守る。**

| 制約 | 理由 |
| --- | --- |
| **Neon 固有機能に依存しない** | ブランチ機能は開発時の検証用途に限定し、**本番のスキーマ管理はマイグレーションファイルで行う** |
| **PostGIS は標準機能のみ使う** | 移行先で同じSQLが動くようにする |
| **接続情報は環境変数で抽象化する** | 接続先の切り替えをコード変更なしで行えるようにする |
| **標準SQLに保つ** | ORM ではなく sqlc で生SQLを書く方針のため、方言に依存しないよう意識する |

これを守れば、移行は `pg_dump` / `restore` とマイグレーションの再適用、および接続先の切り替えで完了する。

## 却下した案

### Cloudflare D1

**再検証の結果、技術的にはCOPANの規模で十分に使えることが確認された。** 当初「地理空間検索が厳しい」と評価したが、これは誤りだった。

| 検証項目 | 結果 |
| --- | --- |
| 空間インデックス | R\*Tree / Geopoly は**有効化されていない**。公式ドキュメントに記載のある拡張は FTS5 / JSON / **Math関数** の3つ |
| 距離計算 | **Math関数があるため Haversine を SQL 内で書ける。** 矩形で絞り込んだ上での距離順ソートが可能 |
| 実用性 | **対象エリアを限定する方針のため、パン屋は数百〜数千件。矩形に入る候補は数件〜数十件であり、実用上まったく問題ない** |
| レイテンシ | 読み取りレプリカを有効化すると全リージョンに読み取り専用コピーが配置されるため、**問題にならない** |
| サイズ上限 | 無料 500MB / 有料（Workers Paid 月$5）10GB。当面十分 |
| コスト | **月$5でWorkers・R2・D1が全て収まる。最安** |

**却下の理由はただ一つ、Go から直接アクセスできないことである。**

D1 は Workers binding からの利用が前提で、外部からは REST API しかない。REST API は管理用途向けとされ Cloudflare 全体のAPIレート制限がかかる。公式ドキュメントが案内する方法は「**D1にアクセスするためのプロキシWorkerを自作する**」であり、これを採用すると構成はこうなる。

```text
ブラウザ → Lambda（Go） → プロキシWorker（TypeScript） → D1
```

言語が2つ、デプロイ先が2つに増え、通信が1往復増える。**Cloudflareに寄せて単純化するつもりが、逆に複雑になる。**

したがって **D1 を選ぶことは TypeScript を選ぶことと同義**であり、[Go採用のADR](./20260812-0659-backend-go-openapi-contract.md)を覆すことになる。今回は Go を優先した。

> **記録として残す**: 「Cloudflare完結（TypeScript + Workers + D1）」は、コスト（月$5前後）とレイテンシの点で客観的に優れた構成である。Go を採用しないのであれば、これが最良の選択肢になる。

## トレードオフとして受け入れること

- **v0.1 の期間中、シンガポール経由で約70msのレイテンシを負う。** 自分専用のため許容する
- **公開前に移行作業が発生する。** データ移行、マイグレーションの再適用、接続先の切り替え、動作確認
- **PlanetScale の PostGIS が復旧しない場合、Supabase となり月$25の固定費が発生する**（当初想定の Neon 従量課金より高い）
- Neon のブランチ機能を環境分離の中核に据えられない（移行時に失うため）

## 結果として必要になる決定

- Neon のリージョン選択（シンガポール `aws-ap-southeast-1` を想定）
- 移行の実施時期（v1.0公開の何週間前に行うか）
- 移行先の最終決定（**着手前に PlanetScale の PostGIS 復旧状況を確認する**）
- G-7 環境分離の方式（Neonのブランチ機能に依存しない形で設計する）
